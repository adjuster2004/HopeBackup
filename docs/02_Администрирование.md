# HopeBackup — администрирование

## Разделы панели

Язык панели — **RU / EN**, переключатель в шапке справа (и на странице входа); выбор запоминается в браузере, при
первом входе берётся язык браузера. На английский переведены надписи панели и каталог (продукты, подключения,
цели, поля параметров); сообщения об ошибках, журналы и названия заданий сервер пока пишет по-русски.

| Раздел | Что делает |

| Серверы и ВМ | Машины по SSH (пароль или ключ): опись до копирования, анализ и рекомендации, установка агента, экземпляры по рекомендациям. Над списком — фильтр (поиск по имени, адресу, ОС, заметкам; состояние агента; состояние описи) и переключатель вида «Карточки / Список» (вид запоминается в браузере, фильтр — в адресе страницы) |

| Коннекторы | SSH-туннель (`-L`, jump-хост), OpenVPN, WireGuard, L2TP/IPsec, IPsec IKEv2, напрямую; состояние канала (интерфейс, адрес, маршруты) |

## Коннекторы VPN

Агент (или сервер) поднимает канал от root на время работы и направляет в него **только трафик до узла
площадки** (`/32`) или явно перечисленных сетей. Маршрут по умолчанию, DNS и маршруты, которые присылает
сервер VPN, не принимаются; внешние скрипты OpenVPN запрещены (`--script-security 1`), опасные директивы
профиля вырезаются. Если сервер и агент стоят на одной машине, канал поднимается один раз и используется
обоими. «Проверить» поднимает канал и обращается к узлу площадки через него.

* **OpenVPN** — профиль .ovpn целиком (сертификаты и ключи — встроенными блоками), логин/пароль при
  `auth-user-pass`, пароль ключа.
* **WireGuard** — «Создать ключи» даёт пару; открытый ключ добавьте пиром на сервере площадки
  (`AllowedIPs` — адрес интерфейса агента). Без модуля ядра используется wireguard-go.
* **L2TP/IPsec** — сервер, общий ключ IPsec, логин и пароль PPP; совместимо с MikroTik, Windows RRAS, Cisco,
  UserGate. Подключение Windows «**L2TP/IPsec с общим ключом**» — это этот тип (не IKEv2): общий ключ тот же,
  логин и пароль — те, что Windows спрашивает при подключении (поле «Имя пользователя» в Windows необязательное,
  но шлюз L2TP их требует).
* **IPsec IKEv2** — site-to-site с PSK (Yandex Cloud VPN Gateway, AWS Site-to-Site VPN: свой ID — внешний
  адрес, сети площадки — `remote_ts`) или удалённый доступ по логину и паролю (EAP-MSCHAPv2) с
  сертификатом CA шлюза.
* «Адрес узла через этот коннектор» — если внутри VPN узел виден по другому адресу.
* Сети записываются адресом сети: `10.77.2.0/24` (запись `10.77.2.10/24` приводится к нему сама).
* **Пакеты VPN — по подтверждению.** После «Сохранить» Ковчег проверяет, есть ли на сервере управления
  пакеты для этого вида коннектора (strongSwan: `strongswan-swanctl`, `charon-systemd`; L2TP — ещё `xl2tpd`, `ppp`;
  `openvpn`; `wireguard-tools`). Если чего-то нет — окно со списком пакетов и командой; «Установить на сервере»
  ставит их заданием с журналом из репозиториев дистрибутива (`apt-get`, `dnf`, `yum`), включает службу
  `strongswan`, выключает системный `xl2tpd`. В том же окне — «Установить на агентах»: агенты, которые пишут на
  площадки через этот коннектор, ставят у себя только недостающее. Окно открывается кнопкой «Пакеты» в строке
  коннектора, а если канал не поднялся из-за пакетов — кнопкой «Установить пакеты» в ячейке «Состояние». Ставить пакеты может только администратор; действие записывается в журнал аудита. Без
  подтверждения пакеты не ставятся: если их нет, канал не поднимается, а ошибка говорит, что установить.
* **Поддержка канала.** Поднятый канал держится, а не поднимается заново на каждую копию. Сторож сервера раз в
  30 с проверяет каналы: возвращает пропавшие маршруты и сам поднимает упавший канал. Если канал
  переподключается сам (xl2tpd дозванивается заново, OpenVPN переподключается), Ковчег ждёт до 40 с, а не рвёт
  его. Перед новым подключением после разрыва — **пауза** («Пауза перед повторным подключением», для L2TP/IPsec
  и IKEv2 по умолчанию 60 с), чтобы шлюз успел закрыть прежний сеанс: иначе шлюз с ограничением «один сеанс на
  пользователя» (UserGate и др.) отклонит новый. После неудач пауза растёт: 30 с, 1, 2, 4, 8, 10 мин; в
  состоянии коннектора видно, когда следующая попытка. Задания и «Проверить» паузу выжидают (пишут об этом в
  журнал), фоновые проверки — нет. При разрыве L2TP и IPsec закрываются явно — шлюз освобождает сеанс сразу.
  Если тем же логином VPN подключаются и люди, и агенты на других машинах, заведите для Ковчега отдельного
  пользователя.

## Восстановление на новую ВМ

Цель «Proxmox VE», «VMware vSphere», «Yandex Cloud» или «AWS EC2» создаёт ВМ при каждом восстановлении:
одноразовый ключ SSH и пользователь `hopebackup` (sudo без пароля) передаются через cloud-init, сервер
ждёт SSH и окончания cloud-init, выполняет `prepare_script` (если задан) и восстанавливает данные по SSH.
Успешная ВМ появляется среди целей как «сервер по SSH»; при сбое удаляется (если не выключено).

| Цель | Что нужно заранее |
|---|---|
| Proxmox VE | API-токен (`user@realm!имя`, права PVEVMAdmin + Datastore.AllocateSpace на хранилище), шаблон с cloud-init-диском и qemu-guest-agent (для DHCP) |
| VMware vSphere 7.0+ | Пользователь с правами клонирования; выключенная ВМ-эталон или шаблон библиотеки; для cloud-init — vSphere 7.0 U3+ и эталон с cloud-init (VMware datasource) и open-vm-tools; иначе — спецификация настройки vCenter и ключ эталона |
| Yandex Cloud | Сервисный аккаунт с ролью `compute.editor` и `vpc.user` в каталоге, авторизованный ключ (JSON); подсеть; для SSH — публичный адрес или доступ сервера к подсети (VPN) |
| AWS EC2 | Ключ IAM с `ec2:RunInstances`, `DescribeInstances`, `DescribeImages`, `DescribeSubnets`, `TerminateInstances`, `CreateTags`; подсеть и группа безопасности с SSH от сервера управления |

Для PostgreSQL на чистой ВМ включите «Установить PostgreSQL той же версии» (репозиторий дистрибутива или
PGDG; ВМ нужен доступ в интернет или к зеркалу). Для qdatabase — шаблон с установленной сборкой.

## Площадка и пароль репозитория

Пароль репозитория расшифровывает мастер-ключ: **без него копии не восстановить**, площадка не может его
сбросить. Храните его вне сервера управления (сейф, разделение между ответственными). Пароль задаётся при
добавлении площадки и используется при «Создать репозиторий».

Уровень сжатия (zstd): 3 — по умолчанию; на узком канале выгоднее 9–15 (больше нагрузка на процессор агента).
Сегменты WAL сжимаются уровнем не ниже 3.

## Серверы и ВМ: опись, анализ, рекомендации

Ковчег осматривает машину до начала копирования — по SSH, без установки чего-либо:

1. **Добавить сервер**: адрес, порт, пользователь. Вход — **по паролю** (подходит и для входа keyboard-interactive
   через PAM) или **по ключу SSH** там, где пароли запрещены (ed25519, ECDSA, RSA; OpenSSH или PEM, с парольной
   фразой). Нужен root или sudo: без пароля, с паролем входа или отдельным «Паролем sudo».
2. **Проверить вход** — права (root, sudo без пароля, sudo с паролем), ОС, ядро, glibc. Ключ хоста запоминается
   при первом подключении; если он изменится, Ковчег откажется подключаться (возможна подмена сервера), пока
   ключ не сброшен кнопкой «Сбросить ключ хоста».
3. **Опись и анализ** — сервер копирует свою программу во временный каталог машины, запускает опись от root и
   удаляет программу. Если программа не запускается (другая архитектура, Alpine без gcompat, каталоги noexec) —
   сокращённая опись командами sh (ОС, ядро, загрузка, железо, диски, сеть, пользователи, процессы, cron).

**Что видно в описи** (вкладка «Система»):

| Раздел | Сведения |
|---|---|
| ОС | дистрибутив, версия и кодовое имя, семейство (Debian, RHEL, SUSE, Alpine, ALT, Astra…), источник сведений (os-release или старые `*-release`) |
| Ядро | версия, сборка, архитектура, параметры загрузки, ядра в /boot, число загруженных модулей |
| Загрузка | UEFI или BIOS, Secure Boot, загрузчик (GRUB 2, GRUB legacy, systemd-boot, extlinux, zipl, LILO) и его файл, пункт по умолчанию, `GRUB_CMDLINE_LINUX`, свои параметры ядра, система инициализации и цель по умолчанию, initramfs (dracut, initramfs-tools, mkinitcpio), разделы /boot и EFI |
| Железо | процессор, память, подкачка, виртуализация (KVM, VMware, Hyper-V, Xen…), облако (Yandex Cloud, AWS, Azure…), cloud-init, гостевые агенты |
| Диски | устройства и разделы с точками монтирования, LVM, RAID, LUKS, подкачка, fstab, корневая ФС |
| Сеть | имя, интерфейсы и адреса, шлюз, DNS, чем настроена сеть (netplan, NetworkManager, ifupdown…) |
| Безопасность | SELinux, AppArmor, файрвол, настройки sshd, FIPS; часовой пояс, синхронизация времени, локаль, репозитории |

Плюс всё, что собирает «Сервер Linux целиком»: процессы и скрипты, задания по расписанию, свои службы, контейнеры,
пользователи, порты, пакеты, узнанные продукты.

**Анализ и рекомендации** — что копировать на этой машине: установить агента, «Сервер Linux целиком» с подобранными
параметрами (домашние каталоги, диски с данными приложений, Docker), отдельные продукты (PostgreSQL с найденными
каталогом программ и портом, GitLab, Vault, MinIO), дампы по расписанию для СУБД без плагина (MySQL, MongoDB,
ClickHouse, etcd), диски и большие каталоги — на выбор. С приоритетами («важно», «желательно»), расписанием и RPO.
Там же — предупреждения (СУБД в контейнерах, сетевые каталоги, нет синхронизации времени) и заметки для
восстановления на новую ВМ: тот же дистрибутив, тип загрузки (UEFI/BIOS), свои параметры ядра, LVM/RAID, прежние
адреса, сетевые каталоги из fstab. Оценка объёма первой копии и места на площадке.

**Подготовка машины** — что донастроить на ВМ до первой копии (в списке машин — значок «донастроить: N»).
У каждого пункта — уровень (нужно сделать / желательно / к сведению), объяснение и готовые команды:

| Что проверяется | Что подсказывает Ковчег |
|---|---|
| Место под снимки LVM | Для каждой группы томов: сколько нужно под снимки копируемых томов (10% тома, не меньше 1 ГиБ на том), сколько свободно, сколько **добавить**. Если не хватает — **пошаговый план** (см. ниже): какой диск добавить и где это сделать в гипервизоре, какие диски не трогать, команды с правильным именем нового диска, проверка |
| LVM thin | Заполнение пула: больше 80% — снимок может переполнить пул, расширьте его (`lvextend`) |
| btrfs, ZFS | Свободно меньше 10% — снимок держит изменённые блоки, место может кончиться во время копии |
| `/boot` без LVM | К сведению: ядра и загрузчик меняются только при обновлении системы — копия согласована, переносить не нужно |
| Тома без LVM/ZFS/btrfs | Снимок невозможен: копия «на ходу». Для согласованной копии — перенос данных на LVM (порядок действий) или режим `pre_snapshot` с остановкой записи |
| Память | Меньше 256 МиБ свободной — агенту не хватит (команды для файла подкачки); меньше 512 МиБ — предупреждение. Агенту во время копии нужно до ~150 МБ |
| Процессор | 1 vCPU — сжатие и шифрование займут ядро на время копии; планируйте копии на ночь |
| Место для агента | `/opt/hopebackup` и `/var/lib/hopebackup`: не меньше 1 ГБ, с PostgreSQL — 5 ГБ (очередь WAL, пока площадка недоступна). Том LVM — команда `lvextend -r` на нужный объём; если в той же группе не хватает места и под снимки — расширение входит в общий план |
| Время | Нет синхронизации времени — `timedatectl set-ntp true` (расписание и PITR зависят от точного времени) |
| Сеть | Сколько займёт первая копия на 100 Мбит/с и 1 Гбит/с; какие порты открыть до сервера управления (4443) и площадки (8443 / 443) |

### Не хватает места под снимки: пошаговый план

Если в группе томов не хватает места под снимки, анализ показывает один план под конкретную машину. Шаги отмечены номерами, у каждого блока команд — кнопка «Скопировать» (комментарии после `#` не копируются).

1. **Добавьте к машине диск N ГБ** — где это сделать, анализ подсказывает по виду виртуализации:
   - vSphere: Edit Settings → Add New Device → Hard Disk;
   - Proxmox: Hardware → Add → Hard Disk;
   - zVirt/oVirt: Диски → «Новый»;
   - Hyper-V, XCP-ng — аналогично;
   - Yandex Cloud, AWS — создать диск и подключить к ВМ.

   Размер считается так: место под снимки с запасом 20%, плюс недостающее агенту, если его том в той же группе; не меньше 5 ГБ.
2. **Найдите новый диск**: пересканирование шины SCSI (перезагрузка не нужна) и `lsblk`.
3. **Включите диск в группу**: `pvcreate` и `vgextend` с именем, под которым диск появится (следующая буква после занятых: `sda`, `sdb` → `/dev/sdc`).
4. **Расширьте том для агента** (`lvextend -r`) — если ему не хватает места.
5. **Проверьте**: `vgs`, `df -h`.
6. **Обновите анализ**: «Опись» ещё раз — пункты станут зелёными.

Красным над шагами — **какие диски не трогать**: занятые диски с размером и тем, что на них смонтировано. Например, «`/dev/sdb` (80 ГБ: `/var/lib/postgresql`)» — `pvcreate` уничтожил бы на нём базу.

**Пример — ВМ Zabbix в vSphere.**

- Диск `sda` (20 ГБ): `/boot` и группа `vg_root` с томами `/`, `/var`, `/var/log`, `/home`.
- Диск `sdb` (80 ГБ) целиком под `/var/lib/postgresql`.
- Под снимки нужно 4 ГБ, а свободно 520 МБ.
- В `/var` агенту не хватает места под спул WAL.

План в этом случае:

```sh
# 1. vSphere: Edit Settings → Add New Device → Hard Disk 12 ГБ (Paravirtual SCSI)
for h in /sys/class/scsi_host/host*/scan; do echo '- - -' > $h; done
lsblk                                  # новый диск sdc 12G — без разделов и точки монтирования
pvcreate /dev/sdc                      # НЕ sdb: там база PostgreSQL
vgextend vg_root /dev/sdc
lvextend -r -L +5G vg_root/lv_var      # /var для агента (спул WAL), без остановки
vgs vg_root                            # VFree ≥ 4 ГБ под снимки
df -h /var                             # свободно ≥ 5 ГБ
```

База на `sdb` снимков не требует: PostgreSQL копируется своими средствами (`pg_basebackup` и архив WAL).

Если добавить диск нельзя, есть два варианта:

- уменьшить «Размер снимка LVM» в параметрах экземпляра — подходит, когда запись во время копии небольшая;
- оставить копию файлов «на ходу».

**Установить агента** — по SSH: программа в `/opt/hopebackup`, одноразовый токен подключения, служба systemd или
OpenRC. После этого отметьте рекомендации, выберите площадку и нажмите **Создать экземпляры по отмеченным**.
Повторное применение не создаёт дубликатов: уже существующие экземпляры пропускаются, а отмеченные диски и каталоги
добавляются в имеющийся «Сервер Linux целиком».

**Безопасность.**
* Имя пользователя и адрес проверяются (латиница, цифры, `. _ -`, не с «-») — их нельзя выдать за опции ssh.
* Смена адреса, порта или пользователя требует заново ввести пароль: сохранённый пароль на новый адрес не уходит.
  Закреплённый ключ хоста сбрасывается только при смене адреса или порта.
* Программа описи и агента пишется на машину сразу от root в каталог root (0700) и сверяется по SHA-256 — пользователь
  машины не может подменить её до запуска. Без прав root опись идёт от пользователя (неполная).
* Пароль sudo передаётся в stdin (`sudo -k -S`), не в командной строке; если sudo пароля не просит (NOPASSWD), он не
  передаётся вовсе. Если sudo требует терминал (`Defaults requiretty`), Ковчег так и сообщит.
* Токен подключения агента передаётся файлом 0600 (не в командной строке), привязан к машине и отзывается по
  окончании установки; агента к машине привязывает сам сервер, а не ответ машины.
* В описи скрываются пароли: параметры fstab (`password=` у CIFS), командные строки процессов и заданий
  (`--password …`, `-pПАРОЛЬ` у mysql, пароль в URL) — опись видят и операторы с ролью «просмотр».
* Каталог программ PostgreSQL принимается только принадлежащий root и не доступный другим на запись.

У экземпляра «Сервер Linux целиком» на странице «Обнаружить» показываются те же анализ и сведения о системе.

## Почта и уведомления

**Почта и уведомления** (только администратор):

1. **Сервер исходящей почты (SMTP)** — сервер организации (Exchange, Postfix, Яндекс 360…), шифрование STARTTLS
   (587), TLS (465) или без шифрования (25 — только доверенный ретранслятор), пользователь и пароль (пусто —
   без входа), адрес и имя отправителя, **адрес панели в письмах** (имя, которое открывается у
   администраторов; пусто — `https://<IP сервера>:4443`). Сертификат сервера почты проверяется по корням
   Mozilla и системному хранилищу; для внутреннего ЦС — поле «Доверенный сертификат ЦС». **Отправить тестовое
   письмо** — с параметрами из формы, до сохранения.
2. **Уведомления** — получатели (адрес группы администраторов) и события галочками. Письмо уходит сразу при
   событии; о том же состоянии повторно не пишем, пока оно не изменится; не больше 20 писем в час по одному
   событию. После сохранения настроек Ковчег заново сообщает о текущих отклонениях (агент не на связи, нарушен
   RPO, мало места…) — о проблемах, начавшихся до включения уведомлений, письмо тоже придёт.
   **Проверить** — письмо получателям со списком выбранных событий.
3. **Журнал отправки** — последние 200 писем: тема, событие, кому, отправлено или текст ошибки.

| Группа | Событие | Когда приходит письмо |
|---|---|---|
| Резервное копирование | Ошибка копирования | задание копирования завершилось ошибкой: экземпляр, агент, ошибка, конец журнала. Для копий по расписанию (и ручных «с повторами») — только когда повторов больше не будет: письмо с числом попыток и причиной |
| | Успешное копирование | каждая готовая копия (объём, новые данные); по умолчанию выключено |
| | Нарушена цель RPO | нет свежей копии дольше цели RPO экземпляра с запасом (¼ цели, не меньше 15 минут); и когда снова в норме |
| | Архив WAL PostgreSQL | отправка WAL с ошибкой или очередь на агенте больше 50 файлов; и когда отправка восстановилась |
| Восстановление | Восстановление | восстановление на агента, сервер по SSH или новую ВМ завершено успешно или с ошибкой |
| Агенты и машины | Агент не на связи | агент не выходит на связь больше 10 минут; и когда снова на связи |
| | Серверы и ВМ | опись или установка агента по SSH не удались; изменился ключ хоста машины |
| | Другие задания с ошибкой | обнаружение, подготовка репозитория, репликация площадок и прочие |
| Хранилище | Мало места | на диске сервера управления или площадки «диск сервера» свободно меньше 10%; и когда освободилось |
| Узлы управления | Узлы управления | принимающий узел не принимает каталог больше 5 минут; активный узел не на связи (письмо шлёт принимающий); управление перешло на другой узел |
| Безопасность | Восстановление доступа к панели | запрошена ссылка сброса пароля; пароль сменён по ссылке или аварийным токеном |
| | Подбор пароля | 5 неудачных входов за 15 минут для одной учётной записи или с одного адреса |

Состояния проверяются раз в минуту на активном узле управления (принимающий проверяет только связь с
активным). Отметки отправленных состояний — `/var/lib/hopebackup/server/notify_state.json`, журнал —
`notify_log.json` (0600).

## Восстановление доступа к панели

Как в HopeDFS — два способа, оба на странице входа (**Забыли пароль?**):

**По почте.** Пользователь вводит имя учётной записи или её адрес почты. Если учётная запись есть, у неё указан
адрес (**Пользователи → Роль и почта**) и почта настроена — на этот адрес уходит **одноразовая ссылка на 30
минут**. Иначе ссылка записывается на сервере управления в `/var/lib/hopebackup/server/password_reset_link.txt`
(0600, только root) — администратор с доступом к консоли сервера откроет её сам. Ответ страницы одинаковый для
любых имён: по нему нельзя узнать, есть ли такая учётная запись. В каталоге хранится только хэш ссылки, поэтому
ссылка работает и на принимающем узле управления. После смены пароля **все открытые сеансы** этой учётной
записи закрываются; администраторам уходит уведомление.

**Аварийно** (закрытый контур, почты нет, доступа к консоли нет). Вкладка «Аварийное» показывает **код запроса**
с отпечатком сервера (machine-id). Передайте его вендору любым каналом — вендор выпускает **токен
восстановления** (подпись RS256 тем же ключом, что лицензии HopeDFS) с новым паролем. Токен принимается только
на этом сервере, до своего срока и **один раз**; пароль задаётся учётной записи из токена (по умолчанию
Administrator, если её нет — создаётся с ролью «Администратор»). Сразу после входа смените пароль.

Ограничение частоты: не больше 10 запросов за 15 минут с одного адреса на каждое действие. Все попытки — в
журнале аудита (`password_reset`).

Смена пароля в **Пользователи** тоже закрывает открытые сеансы пользователя (свой сеанс продолжает работать).

## Исключения

**Настройки → Исключения** — что не копировать ни у одного экземпляра «Файлы и каталоги» и «Сервер Linux целиком»
(если у экземпляра не выключено «Общие исключения сервера»). У экземпляра — свой список и предел размера файла.

| Шаблон | Что исключает |
|---|---|
| `/var/log` | путь от корня и всё внутри |
| `/home/*/Downloads` | `*` — любое имя каталога (без `/`) |
| `*.log`, `node_modules`, `.cache` | имя файла или каталога на любой глубине |
| `build/tmp`, `**/target/debug` | часть пути на любой глубине (`**` — любое число каталогов) |

Каталог, указанный у экземпляра явно, общие исключения не отменяют (например, `/tmp/app` при общем `/tmp`).
По умолчанию исключены служебные и временные каталоги: `/proc`, `/sys`, `/dev`, `/run`, `/tmp`, `/var/tmp`,
`/var/cache`, списки пакетов, журнал systemd, файлы подкачки, `.cache`, `*.swp`, `*.tmp`. `/var/log` — одной
кнопкой в «Добавить».

## Сервер Linux целиком

Продукт «Сервер Linux целиком» (агент — от root) сначала составляет **опись** («Обнаружить» на странице экземпляра):

* **процессы**: исполняемый файл и, для интерпретаторов (sh, bash, python, perl, php, node, java -jar…), сам
  скрипт; служба systemd; принадлежность пакету. Всё, что не из пакетов, — «приложение»: его каталог
  (`/opt/app`, `/srv/x`, каталог скрипта) копируется целиком, если меньше предела (2 ГБ), иначе — файлы запуска
  («Копировать целиком» добавляет каталог в «Дополнительные пути»);
* **по расписанию**: `/etc/crontab`, `/etc/cron.d`, cron.daily/…, пользовательские crontab, anacron, at,
  таймеры systemd — и скрипты, которые они запускают;
* **свои службы systemd** и то, что они запускают;
* **диски**: отдельные разделы, сетевые каталоги (NFS, SMB, sshfs, rclone…), bind-монтирования с занятым местом —
  копируются, только если отметить «Копировать» (каждый — отдельной частью копии);
* **Docker**: контейнеры, compose-проекты (копируются), тома и привязанные каталоги (по параметру `volumes`);
* **пользователи** (пароль, ключи SSH, sudo, crontab), открытые порты, пакеты, установленные вручную;
* **узнанные продукты** (PostgreSQL, GitLab, Vault, MySQL…) — подсказка добавить их отдельным экземпляром;
  каталоги данных СУБД в файловую копию не попадают (файлы работающей СУБД несогласованны).

Копия: `/etc` целиком, пользователи и группы с хэшами паролей (`passwd`, `shadow`, `group`, `gshadow`),
`/root`, домашние каталоги (целиком или только `.ssh` и профили), `/usr/local/{bin,sbin,etc}`, спулы cron и at,
приложения, отмеченные диски, опись. Память процессов не сохраняется: после восстановления программы
запускаются заново своими службами и заданиями.

Восстановление (мастер, параметр «Что восстановить»):

* **Пользователи** — создаются отсутствующие группы и пользователи с теми же UID/GID (если заняты — другие,
  владелец домашнего каталога исправляется), пароли из копии, членство в группах, ключи SSH с правами 700/600,
  правила `/etc/sudoers.d` после проверки `visudo -c`. Пароль root — только по флажку.
* **Части копии** — `system`, `homes`, `apps`, `docker`, `mount-…` в отдельный каталог или на место (`/`);
  «Только пути» ограничивает, например, `/opt/app`. На место не заменяются файлы, определяющие машину:
  `fstab`, `hostname`, `hosts`, сеть, `machine-id`, `passwd/shadow`, ключи хоста SSH (по флажку).
* **Сервер целиком** — на новую машину (в том числе новую ВМ): пользователи → пакеты из описи (тот же
  дистрибутив) → файлы → включение своих служб и таймеров systemd.

## Площадки на диске и в облаке

* **Диск сервера управления** — каталог на большом диске сервера (`/mnt/data/hopebackup`). Сервер сам обслуживает
  его как узел хранения по адресу `https://сервер:4443/node/<id>`: агенты пишут через порт панели, токены и
  отпечаток подставляются автоматически. Свободное место видно в карточке площадки. Такая площадка не защищает
  от потери самого сервера — добавьте принимающую площадку на другой площадке или в облаке.
* **Принимающая площадка** указывается у источника: площадка-источник → «Изменить» → «Принимающие площадки».
  Пароль репозитория у неё — тот же, что у источника, имя репозитория — любое свободное. Репозиторий на ней
  создаёт **первая репликация** — копией исходного («Синхронизировать сейчас» у источника); «Создать репозиторий»
  у принимающей площадки не показывается и не выполняется. В карточке такой площадки — строка «Принимает копии с».
  Если на ней под этим именем уже есть другой репозиторий, репликация остановится с подсказкой указать другое имя.
* **Google Диск** — приложение OAuth в Google Cloud (тип «TVs and Limited Input devices», включён Google Drive API),
  Client ID и секрет → «Подключить» → открыть ссылку, ввести код, разрешить доступ. Права — `drive.file`:
  HopeBackup видит только свою папку. Объекты хранятся в одной папке, путь — в имени файла.
* **Яндекс Диск** — приложение на oauth.yandex.ru с правом «Доступ к папке приложения на Диске» → «Подключить»
  (код на странице Яндекса) или готовый токен OAuth. Папка по умолчанию — `app:/HopeBackup`. Токен живёт год;
  при входе по коду сервер продлевает его сам за 30 дней до конца.
* **Nextcloud / WebDAV** — адрес (`https://облако/remote.php/dav/files/ЛОГИН`), логин и **пароль приложения**
  (Nextcloud: Настройки → Безопасность). Подходит ownCloud, Synology и Яндекс Диск по WebDAV
  (`https://webdav.yandex.ru`, пароль приложения).

У облачных дисков нет защиты от удаления (Object Lock): доступ агентов позволяет удалять файлы в папке площадки.
Данные зашифрованы паролем репозитория; для защиты от удаления держите копии ещё и на узле HopeBackup или в S3 с
Object Lock (принимающая площадка). Облака ограничивают частоту запросов — клиент повторяет запросы при 429/5xx.

## Расписание и хранение

* Полная копия — cron из 5 полей в местном времени сервера (`0 1 * * *` — ежедневно в 01:00).
* Для PostgreSQL отдельно — логический дамп баз (`dump`), если базы указаны в параметрах.
* WAL PostgreSQL отправляется непрерывно; `archive_timeout = 60s` ограничивает RPO при малой нагрузке.
* **Журнал** (MySQL/MariaDB — архив binlog, MS SQL — журнал транзакций): отдельное расписание «Журнал …»
  (по умолчанию каждые 15 минут) и кнопка с тем же названием у экземпляра. Копия журнала начинается с полной
  копии: без неё задание сообщит «сначала нужна полная копия».
* Хранение: сколько последних копий держать — отдельно для каждого вида (полные, дампы). Копии журнала
  хранятся, **пока хранится полная копия, с которой начинается их цепочка** (счётчик на них не действует):
  удалить журнал раньше его полной — потерять восстановление на момент. Очистку выполняет узел после каждой
  успешной копии, если у площадки задан токен администратора узла. Сегменты WAL старше самой старой
  оставшейся полной копии удаляются.

## Повторы и пропущенные запуски

**Настройки → Повторы и пропущенные запуски** — общая политика; у экземпляра на вкладке «Расписание» можно
оставить её («Как в настройках сервера») или задать свою.

* **Повторы при ошибке**: включено, число повторных попыток (0–24, по умолчанию 3) и пауза перед каждой
  (1–1440 минут, по умолчанию 60). Копия в 01:00 не удалась — повторы в 02:00, 03:00, 04:00. В журнале
  неудачного задания: «повтор в HH:MM (попытка 2 из 4)», у повторного задания — метка «повтор, попытка N».
  Повтор не запускается, если копию уже снял другой запуск (вручную или по расписанию) или если задание
  этого экземпляра уже идёт — тогда повтор ждёт его окончания. Письмо «Ошибка копирования» приходит один
  раз — когда повторов больше не будет («повторов больше не будет: попыток 4, последняя ошибка …»).
* Повторяются копии **по расписанию**, повторы и догоны. Ручная копия из панели не повторяется (её итог
  виден сразу); из API или скриптов — с `"retry": true` (метка «вручную, с повторами»). Обнаружение,
  восстановление и прочие задания не повторяются.
* **Догон пропущенного запуска** (включён по умолчанию): если сервер управления был выключен в момент запуска
  по расписанию, после включения он один раз запускает пропущенную копию (метка «догон»), если пропуск не
  старше окна (по умолчанию 24 часа) и после него копий этого вида не было. Пропущенных запусков может быть
  несколько — догоняется один, последний.
* Если итог задания не дошёл до сервера, но копия на площадке есть (снапшот с номером задания), повтор не
  делается: задание отмечается успешным («снапшот найден на площадке»).

## Снимки файловых систем

Файловая копия («Файлы и каталоги», «Сервер Linux целиком») по умолчанию читает данные **из снимка** тома —
все файлы в одном состоянии на момент снимка, даже если приложение пишет во время копии.

| ФС | Как снимается | Требования |
|---|---|---|
| LVM (обычные тома) | `lvcreate -s` на 10% тома (не меньше 1 ГиБ), монтируется только для чтения в `/run/hopebackup/snap/…` | Свободное место в группе томов (см. «Подготовка машины») |
| LVM thin | снимок тонкого тома (`-kn`), место не резервируется | Запас в тонком пуле |
| ZFS | `<набор>@hopebackup-<задание>`, чтение из `.zfs/snapshot` | — |
| btrfs | снимок подтома только для чтения в `<точка>/.hopebackup-snap/` | Свободное место |

Параметры экземпляра: **Снимок файловой системы** — `auto` (по умолчанию: снимок, где возможно; иначе копия
«на ходу» с предупреждением в журнале), `required` (без снимка копия завершается ошибкой с советом),
`off`; **Размер снимка LVM, %**; **Команда перед снимком** (например, сбросить буферы приложения или
заблокировать запись) и **Команда после снимка** (выполняется сразу после снимков, даже при ошибке — снять
блокировку). После копии проверяется заполнение снимка LVM: если он переполнился, копия завершается
ошибкой (данные в нём недостоверны) — увеличьте размер.

Снимки удаляются по окончании копии; снимки, оставшиеся после падения агента или машины, агент убирает
при запуске и перед следующей копией. В свойствах снапшота — «снимок ФС: да/нет».

## Обрывы и падения во время копии

Снапшот на площадке появляется **последним шагом**, после всех данных: оборванная копия не оставляет
«битой» точки восстановления, а уже отправленные блоки используются следующей попыткой (докачивается
только недостающее). Несвязанные блоки прерванной копии сборка мусора удаляет не раньше чем через час.

| Что случилось | Что происходит |
|---|---|
| Сервер управления упал посреди копии | Агент продолжает и завершает копию. Итог сохраняется на агенте (`/var/lib/hopebackup/outbox/`, 0600) и отправляется, когда сервер снова на связи. Перезапущенный сервер 15 минут ждёт итогов от агентов («ждём итог от агента»), только потом считает задания прерванными |
| Связь агента с площадкой пропала | Агент ждёт площадку до 10 минут (паузы 1, 2, 4 … 30 с) и продолжает с места обрыва. Дольше — копия завершается ошибкой «площадка недоступна дольше 600 с», дальше — повторы по политике |
| Агент или машина перезапустились посреди копии | Сервер видит это по следующему отчёту агента (агент запущен позже начала задания) и сразу отмечает задание прерванным — затем повтор. Снимки ФС убираются при запуске агента |
| Итог задания потерян | Перед повтором сервер ищет на площадке снапшот этого задания; если он есть — задание успешно |
| Сервер был выключен во время запуска по расписанию | Догон пропущенного запуска после включения |

Временные каталоги программы описи и установки (`hopebackup.XXXXXX` в `/var/tmp`, `/tmp`, `/root`…), оставшиеся
после обрыва SSH, удаляются при следующей описи или установке (старше часа).

## Найдено на серверах — не защищено

Каждый агент раз в 6 часов, а первый раз через минуту после запуска, смотрит, что работает на его сервере: процессы, контейнеры, открытые порты. Полную опись при этом он не снимает. Если найден продукт, для которого есть штатный способ копирования, а экземпляра для него на этом сервере ещё нет, на «Обзоре» и на странице «Продукты» появляется блок **«Найдено на серверах — не защищено»**. Примеры:

* **GitLab** (Omnibus или контейнер) — штатный `gitlab-backup` вместе с `gitlab.rb` и `gitlab-secrets.json` (без секретов не восстановить CI-переменные, токены и 2FA);
* **PostgreSQL** (в том числе встроенная PostgreSQL GitLab), **MySQL/MariaDB**, **MongoDB** и другие СУБД — согласованная копия средствами СУБД вместо файлов;
* **Vault / OpenBao**, **libvirt/KVM**, **Kubernetes** и т. п.

**«Защитить»** создаёт экземпляр с рекомендованными параметрами и ночным расписанием на выбранной площадке (если площадка одна, она подставляется сама) и открывает его страницу, где можно сразу запустить «Полную копию» или поменять параметры. **«Не предлагать»** скрывает находку для этого сервера (например, она копируется другим способом); действие записывается в журнал аудита. Второстепенное, конфигурация чего и так попадает в копию сервера целиком (nginx, haproxy, OpenVPN), не предлагается: при желании такой экземпляр создаётся вручную. Нужен агент 0.8.8 или новее.

## Подключение к PostgreSQL: пользователь ОС и роль СУБД

Агент запускает `psql`, `pg_basebackup` и `pg_dump` на сервере СУБД от имени **«Пользователь ОС сервера СУБД»** (`os_user`) и входит в СУБД под ролью **«Пользователь СУБД»** (`user`). Поля находятся на странице экземпляра → вкладка «Параметры» → блок «Параметры плагина».

При входе через сокет (`/var/run/postgresql`, по умолчанию) PostgreSQL на Debian/Ubuntu, РЕД ОС и Astra проверяет вход методом `peer`: роль пускается, только если имя пользователя ОС совпадает с ней. Пароль при этом не используется. Отсюда ошибка `FATAL: Peer authentication failed for user "zabbix"`: программы запущены от `root`, а роль — `zabbix`.

| Вариант | Хост | Пользователь СУБД | Пользователь ОС | Пароль |
|---|---|---|---|---|
| **Рекомендуется** — через сокет | `/var/run/postgresql` | `postgres` | `postgres` | не нужен (кнопка «Удалить пароль», если задан) |
| По паролю через сеть | `127.0.0.1` | роль с `REPLICATION` и правами суперпользователя | `postgres` | пароль роли |
| Встроенная PostgreSQL **GitLab Omnibus** | `/var/opt/gitlab/postgresql` | `gitlab-psql` | `gitlab-psql` | не нужен |

Если по указанному «Хосту» сокета нет, а PostgreSQL на сервере работает, агент находит работающий кластер сам: каталог сокета и порт берёт из его `postmaster.pid`. Если «Пользователь СУБД» оставлен по умолчанию (`postgres`), агент подставляет владельца кластера (у GitLab — `gitlab-psql`). Если указан «Каталог бинарников», подходит только кластер этих программ. В журнале задания и на обзоре экземпляра появляется предупреждение, что именно подставлено: эти значения лучше записать в параметры. Встроенная PostgreSQL GitLab перезапускается командой `gitlab-ctl restart postgresql`, её же выполняет кнопка «Перезапустить PostgreSQL».

**Способ базовой копии** («Параметры плагина» → «Способ базовой копии», по умолчанию `auto`). Обычно копия снимается `pg_basebackup` по репликационному подключению. Если оно закрыто настройками кластера — `max_wal_senders = 0` или в `pg_hba.conf` нет правила `replication` (так у встроенной PostgreSQL GitLab), — агент сам делает **низкоуровневую копию**: в одном сеансе `pg_backup_start` → каталог данных потоком tar прямо в хранилище → `pg_backup_stop` с ожиданием архивации WAL; `backup_label` кладётся в копию. Восстанавливается она так же, как копия `pg_basebackup`, в том числе на момент времени. Нужны только права суперпользователя и чтение каталога данных агентом (он работает от root); табличные пространства (`pg_tblspc`) таким способом не копируются. Значения `basebackup` и `lowlevel` задают способ явно. Опись сервера с GitLab сразу предлагает экземпляр «PostgreSQL GitLab (встроенная)» с этими параметрами.

Роль приложения (например, `zabbix`) обычно не подходит: ей не хватает прав `REPLICATION` для `pg_basebackup` и прав суперпользователя для настройки архива WAL (`ALTER SYSTEM`). Ковчег копирует кластер целиком, все базы сразу, поэтому достаточно служебной роли `postgres`.

Если подключиться не удалось, в красном сообщении на вкладке «Обзор» под текстом ошибки PostgreSQL написано, что она значит и какие поля исправить, и есть кнопка «Открыть параметры». Подсказки есть для `peer`/`ident`, неверного или незаданного пароля, несуществующей роли, отсутствующего правила в `pg_hba.conf`, неработающего сервера (сокет не найден) и нехватки прав на `ALTER SYSTEM`.

## Архив WAL PostgreSQL: где настроить

Полная копия PostgreSQL создаётся только при включённом архиве WAL. Без журнала её нельзя восстановить, поэтому копия завершится ошибкой «архивация WAL для этого экземпляра не настроена». Настройка — на странице экземпляра:

**«Резервное копирование» → «Продукты» → экземпляр PostgreSQL → вкладка «Обзор» → блок «Архив WAL».**

Блок с тремя шагами там же, где «не настроен», и в красном сообщении об ошибке копии:

1. **«Настроить архив WAL».** Агент сам:
   - включает `archive_mode = on` (и `wal_level = replica`, если было `minimal`);
   - прописывает `archive_command` — сегменты складываются в спул агента `/var/lib/hopebackup/spool/…` и уходят на площадку;
   - ставит `archive_timeout = 60s` и перечитывает конфигурацию.

   Нужна роль оператора или администратора.
2. **«Перезапустить PostgreSQL».** `archive_mode` применяется только при перезапуске. База при нём несколько секунд недоступна, поэтому кнопку нажимает администратор в удобное время, после подтверждения. Агент сам выбирает способ перезапуска именно этого кластера, команду из панели он не принимает:
   - служба systemd, в которой работает процесс СУБД, например `systemctl restart postgresql@16-main` (на Ubuntu общая `postgresql.service` — только обёртка);
   - без systemd на Debian/Ubuntu — `pg_ctlcluster 16 main restart`;
   - иначе — `pg_ctl restart -m fast` от пользователя СУБД.

   Затем агент ждёт, пока СУБД снова примет подключения (до 2 минут), и проверяет, что `archive_mode = on` и перезапуска больше ничего не ждёт. Пока у экземпляра идёт копия или восстановление, перезапуск не запускается. Кнопка работает с агентом 0.8.3 и новее. Если агент старше, вместо неё панель предложит обновить его («Обновления» → таблица агентов → «Обновить») или перезапустить СУБД вручную. Команда видна и под кнопкой («или вручную на сервере»), если удобнее перезапустить самому. Действие записывается в журнал аудита.
3. **«Полная копия».** После перезапуска в блоке «Архив WAL» появится «Архив WAL включён — осталось сделать первую копию» с кнопкой. После копии станет доступно восстановление на момент времени.

Нужен ли перезапуск, видно и в блоке «Обнаружение на агенте»: строка «Перезапуск СУБД: нужен».

Проверить на сервере: `psql -c "show archive_mode" -c "show archive_command"` — должно быть `on` и команда `hopebackup wal-push …`.

## Восстановление PostgreSQL

* **На момент времени (PITR)**: указывается время с часовым поясом (`2026-10-24 14:31:00+03`); берётся
  ближайшая предшествующая полная копия, дальше применяется журнал WAL.
* **Готовая точка**: восстановление до конца доступного журнала после копии.
* Цель: пустой каталог данных (`pgdata`), пользователь ОС СУБД, порт (если на цели уже работает другой
  кластер). На цели должна быть установлена та же мажорная версия PostgreSQL (или та же сборка qdatabase).
* Восстановленный кластер стартует с `archive_mode = off`, чтобы проверочная копия не писала журнал в
  репозиторий продуктива. Для перехода на него в продуктив включите архивацию заново («Настроить архив WAL»
  у экземпляра, указывающего на новый сервер).
* «Через сервер» — данные идут с площадки через сервер управления (обратный SSH-туннель): цели не нужен
  сетевой доступ к площадке.
* Одна база из логического дампа — режим `dump` в работающий сервер на цели.

## GitLab, Vault, S3

* **GitLab** — `gitlab-backup create STRATEGY=copy` без сжатия (`COMPRESS_CMD=cat`, GitLab 16.7+; старее —
  `GZIP_RSYNCABLE=yes`): неизменённые репозитории не передаются повторно. В копию входят `gitlab.rb`,
  `gitlab-secrets.json` (без него не расшифровать CI-переменные, токены, 2FA) и сертификаты; локальный архив
  удаляется. Восстановление — только в ту же версию GitLab (можно поставить её на чистую машину), затем
  `gitlab-ctl reconfigure`, `gitlab-backup restore`, перезапуск и `gitlab:check`, `gitlab:doctor:secrets`.
  Для Docker укажите контейнер.
* **Vault / OpenBao** (raft) — токен с правом `read` на `sys/storage/raft/snapshot`. Восстановление —
  в инициализированный и разблокированный кластер (`snapshot-force` для нового кластера); после этого Vault
  разблокируется ключами **исходного** кластера (HopeBackup их не хранит).
* **S3** — ключ только на чтение; бакеты целиком или по префиксу, исключения. Восстановление — в тот же или
  другой бакет (в том числе другого хранилища), с созданием бакета.

## Продукты Hope

Hope Mail Server, Hope MSG Gateway, HopeInventory, HopeDFS, HopeDC — агент находит службу по юниту systemd
(`hopedb`, `hope-msg-gateway`, `hopeinv`, `hopedfs`, `hopedc`), её каталоги — по переменным юнита
(`DB_DATA_DIR`, `HOPEINV_DATA`, `DC_DATA_DIR` …), WorkingDirectory и файлам настроек продукта.

* **Согласованность** («auto»): один снимок ФС на все части (LVM, ZFS, btrfs); без снимка — служба
  останавливается только на время копии данных, которым это нужно, и сразу запускается (в журнале — «службы …
  были недоступны N с»). HopeDFS без снимка не останавливается (файловый сервер): копия на ходу.
* **Hope Mail Server**: WAL и настройки (`DB_DATA_DIR`) — при остановке, тела писем (`BLOB_DATA_DIR` или основное
  хранилище из `storage.json`) — после запуска (тела пишутся раньше ссылок на них). Без встроенных бэкапов
  `hopedb_backups` и метки `restore_pending.txt`.
* **Hope MSG Gateway**: `msg_local_data` (состояние, очередь, карантин, ящики) без антивирусных баз и пакетов
  обновлений; мастер-ключ `/etc/hope-msg/master.key` (по флажку), keepalived, помощники `hope-msg-*-apply`.
* **HopeInventory**: настройки, `hopeinv.redb`, TLS, журнал аудита.
* **HopeDFS**: каталог узла и кластера, каждая шара отдельной частью **с NTFS-правами** (`user.hopedfs.*`
  в расширенных атрибутах), без «Предыдущих версий» и временных файлов репликации (по флажкам — с ними).
  После восстановления участника группы репликации исключите его из группы и добавьте заново.
* **HopeDC**: база (ewal), SYSVOL, PKI, кластер; мастер-ключ — `hopedc-core key export` с паролем экспорта
  (параметр «Пароль экспорта ключа»; без него ключ в копию не попадает — храните его сами). Восстановление:
  `full` — база из копии (узел становится неавторитетной копией, остальные узлы пересоберите), `rejoin` —
  только `cluster_config.json` и ключ: узел заберёт данные у живого пира. Нужен «Пароль ключа из копии».
* Восстановление на место: служба останавливается, данные заменяются целиком (прежние — рядом,
  `<каталог>.before-restore-<время>`), владелец — пользователь службы, служба запускается, проверяется ответ
  по HTTPS. «Корень восстановления» ≠ `/` — только распаковать для проверки.

## СУБД

| Продукт | Как копируется | На агенте нужно |
|---|---|---|
| **MySQL / MariaDB** | дамп `mysqldump`/`mariadb-dump --single-transaction` или физическая `mariabackup`/`xtrabackup` потоком xbstream (auto — физическая для баз больше 20 ГБ); журнал — закрытые файлы binlog (`FLUSH BINARY LOGS`) | клиент MySQL/MariaDB; для физической — mariabackup (mbstream) или xtrabackup той же версии; для журнала — `log_bin` |
| **MS SQL Server** | `BACKUP DATABASE` (полная), `BACKUP LOG` (журнал; у баз в модели SIMPLE — разностная) в промежуточный каталог сервера, файл .bak — потоком и удаляется | `sqlcmd` (mssql-tools18 или go-sqlcmd); каталог `stage_dir`, доступный и SQL Server, и агенту |
| **MongoDB** | `mongodump --archive` (у набора реплик — `--oplog`) прямо в репозиторий | MongoDB Database Tools (для автоопределения набора реплик — `mongosh`) |
| **Redis / Valkey** | снимок RDB по протоколу репликации (`redis-cli --rdb`), без остановки; redis.conf и ACL | `redis-cli` |
| **ClickHouse** | `BACKUP DATABASE … TO Disk('backups', …)` и каталог копии с диска; или схема и данные `FORMAT Native` | `clickhouse-client`; для BACKUP — диск копий в конфигурации сервера |

* Пароли — во временных файлах 0600 (`--defaults-extra-file`, `--config`, `--config-file`) или в окружении
  (`SQLCMDPASSWORD`, `REDISCLI_AUTH`), не в командной строке. СУБД в контейнере — параметр «Контейнер Docker»:
  утилиты выполняются в нём (`docker exec`), секреты — файлом внутри контейнера.
* **Восстановление на момент** (MySQL, MS SQL): «Момент восстановления» `ГГГГ-ММ-ДД ЧЧ:ММ:СС` — берётся ближайшая
  предшествующая полная копия, затем журнал: MySQL — `mysqlbinlog --start-position … --stop-datetime | mysql`,
  MS SQL — цепочка `RESTORE … NORECOVERY` (полная → последняя разностная → журналы, последний со `STOPAT`) и
  `RECOVERY`. Выбрана копия журнала — восстановление до её конца.
* **Одна база под другим именем** — рядом с рабочей: MySQL (из полного дампа), MS SQL (файлы переименовываются
  `MOVE`), MongoDB (`--nsFrom/--nsTo`), ClickHouse (`RESTORE … AS`). Существующая база ClickHouse переносится в
  `<имя>_before_restore_<время>`.
* MySQL, физическая копия: на место — остановка службы, prepare, прежний каталог данных рядом, `--move-back`,
  владелец `mysql`, запуск; или «Каталог для физической копии» — только распаковать и подготовить.
* Redis: на место — служба (или контейнер) останавливается; при включённом AOF копия становится базой AOF
  (иначе сервер загрузил бы прежний AOF).

## Инфраструктура и платформы

* **Keycloak** (Quarkus 17+): выгрузка realm с пользователями (`kc.sh export --users realm_file`, от пользователя
  службы, с её окружением), `conf/`, `providers/`, `themes/`; встроенная H2 — каталогом `data/`. Базу Keycloak
  (PostgreSQL и т. п.) добавьте отдельным экземпляром плагина СУБД. Восстановление — `kc.sh import --override`.
* **FreeIPA / LDAP**: OpenLDAP — `slapcat` cn=config и каждой базы (mdb — на ходу), восстановление `slapadd` в
  чистый каталог (прежний рядом), владелец `openldap`/`ldap`; FreeIPA — `ipa-backup --data --online` (или полная
  с остановкой служб), восстановление `ipa-restore` (нужен пароль Directory Manager).
* **Docker**: каждый именованный том — с паузой (`pause`) или остановкой контейнеров, которые его используют,
  только на время копии этого тома; проекты compose — каталогом (compose.yml, .env); описание контейнеров;
  по желанию образы (`docker save`). Восстановление: том создаётся с теми же драйвером и метками, прежнее
  содержимое рядом, контейнеры останавливаются на время записи; проекты — `docker compose up -d`.
  Контейнер в цикле перезапусков (`restarting`) Docker приостановить не даёт: его данные копируются без паузы,
  копия не прерывается, а на обзоре экземпляра появляется «Последняя копия создана, но есть предупреждения»
  с именем контейнера и командой `docker logs` для проверки. Так же, если контейнер ушёл в перезапуск прямо во
  время паузы. Ошибкой копия завершается, только если не удалось приостановить работающий контейнер.
* **Kubernetes / minikube / k3s**: объекты API по типам ресурсов (без событий, подов и ReplicaSet — их
  пересоздают контроллеры), снимок etcd (`etcdctl snapshot save` на узле управления kubeadm), тома
  hostPath/local (для minikube с драйвером docker — «Контейнер узла» = `minikube`), `/etc/kubernetes`.
  Восстановление: служебные поля очищаются, объекты применяются по порядку зависимостей; снимок etcd — только
  файлом (`etcdutl snapshot restore` вручную).
* **Jenkins**: JENKINS_HOME без `workspace`, кэшей и распакованного war (по флажкам — без истории сборок и с
  артефактами); на ходу (снимок ФС, если есть) или с остановкой (`consistency = stop`).
* **Nexus / Harbor**: Nexus — каталог `sonatype-work` (БД, настройки, ключи) согласованно, хранилища blob —
  после; без журналов и индекса поиска. Harbor — `pg_dumpall` из `harbor-db`, `/data/secret`, хранилище образов,
  `harbor.yml`; восстановление: остановка, файлы, база, `docker compose up -d`.
* **Zabbix / Grafana**: Zabbix — дамп базы (MySQL или PostgreSQL; по желанию без данных `history*`/`trends*`),
  `/etc/zabbix`, скрипты оповещений; Grafana — `grafana.db` согласованной копией SQLite (`sqlite3 .backup`) или
  дамп внешней базы, плагины, provisioning.
* **Elasticsearch / OpenSearch**: Snapshot API. Репозиторий fs — каталог из `path.repo` (в кластере — общий для
  всех узлов): кластер пишет снимок, HopeBackup забирает каталог (неизменённые сегменты не передаются повторно),
  в каталоге остаётся только последний снимок. Свой репозиторий кластера (S3 и т. п.) — HopeBackup только создаёт
  снимки. Восстановление — через отдельный репозиторий только для чтения: существующие индексы закрываются
  или восстанавливаются с префиксом.

## Образ ВМ целиком

Копия ВМ — описание и диски целиком потоком в репозиторий; одинаковые блоки дисков между копиями не
передаются повторно (передаётся весь диск, хранится только новое).

| Платформа | Как | Доступ |
|---|---|---|
| libvirt / KVM | внешний снимок дисков (`snapshot-create-as --disk-only`, заморозка ФС через qemu-guest-agent), слои qcow2, затем `blockcommit --shallow --pivot` | агент на гипервизоре или узел по SSH (root или sudo) |
| Proxmox VE | `vzdump --mode snapshot --stdout --compress 0`, восстановление `qmrestore -` / `pct restore` | агент на узле или узел по SSH; ВМ других узлов — через SSH кластера |
| oVirt, zVirt, РОСА, HOSTVM | API резервного копирования ВМ (Engine 4.4+) и imageio, восстановление — новые диски и ВМ | учётка Engine (`admin@internal`) |
| OpenNebula, ПК СВ «Брест» | XML-RPC + libvirt узла; восстановление — образы и шаблон | учётка `oneadmin`, SSH к узлам |
| OpenStack | снимок Nova / выгрузка тома Cinder, загрузка из Glance | Keystone v3, роль admin проекта |
| VMware vSphere | снимок, экспорт NFC (streamOptimized VMDK), OVF; CBT — учёт изменённых блоков; восстановление ImportVApp | vCenter или ESXi, роль с правами снимков и экспорта |
| XCP-ng, Citrix Hypervisor | снимок → XVA без сжатия; восстановление — импорт в SR | root или роль Pool Operator |
| Nutanix AHV | образ из диска ВМ (клон) → загрузка; восстановление — образы и ВМ | Prism Central v3 |
| SpaceVM, VMmanager 6 | API платформы + libvirt узла по SSH | ключ интеграции / учётка; SSH к узлам |

* Восстановление: на ту же платформу (новое имя, хранилище, узел/кластер, сеть) или «Только файлы в каталог» —
  диски и описание для импорта вручную или на другую платформу. SpaceVM и VMmanager — файлами на узел (их API
  не принимает образ диска потоком): импортируйте диски средствами платформы.
* vSphere CBT: передаётся весь диск (чтение только изменённых блоков требует VDDK), в журнале — сколько
  изменилось с прошлой копии.

## Образ машины по SSH и образы qcow2

**«Образ машины по SSH»** — копия дисков физической или виртуальной машины целиком, без агента на ней.
Машина выбирается из «Серверы и ВМ» (кнопка «Образ дисков» у машины — продукт с уже выбранной машиной);
выполняет сервер управления (или агент, если машина доступна только из его сети). Сервер подключается по SSH,
на время копии кладёт на машину свою программу и читает диски блоками по 4 МиБ: тома LVM — через снимок
(`lvcreate -s`, нужно свободное место в группе томов), небольшие разделы с ФС (`/boot`) — с заморозкой,
остальное — на ходу (в журнале предупреждение), подкачку — нулями. В репозиторий блоки ложатся как у прочих
продуктов: с дедупликацией, шифрованием, репликацией и хранением по политике; следующая копия передаёт только
изменившиеся блоки. Точка восстановления → **«Развернуть»** (ВМ на Proxmox VE, libvirt/KVM, oVirt/zVirt,
OpenStack с параметрами источника) или выгрузка файлов qcow2/vmdk/vhd/raw; **«Скачать .qcow2»** — только
администратор, размер показывается до скачивания, каждое скачивание — в журнале аудита.

**«Образы qcow2» (доп. канал)** — готовые файлы образов по своему расписанию. Путь данных:

1. машина → по SSH → **сервер HopeBackup**: блоки в репозиторий;
   Площадка в форме не выбирается — та же, что у источника (оттуда берётся копия). Форма показывает,
   **сколько места понадобится**: до первой копии — по описи дисков машины (если описи нет — кнопка
   «Снять опись машины»), после — точно по копии; рядом — свободно в папке сервера и на площадках.
   **К серверу управления должен быть подключён диск большого объёма**: каждый хранимый набор занимает
   примерно столько, сколько данных на дисках машины;
2. сервер **сам собирает и конвертирует** последнюю копию в qcow2 — в **локальной папке** на подключённом к нему
   диске (в форме — список дисков сервера со свободным местом, например `/mnt/data` → `/mnt/data/hopebackup-images`).
   Агент в этом не участвует. Форма до создания показывает, сколько места займут образы; при нехватке места
   сборка не начинается. Хранится последних N наборов (`ГГГГММДДTччммссZ`); продукт удаляет только свои наборы;
3. готовый qcow2 **копируется на площадки, включённые на закладке «Репликация»** карточки «Образов qcow2»
   (узлы HopeBackup; по умолчанию никуда) и лежит там открыто, рядом
   с репозиторием: `<данные узла>/images/<репозиторий>/<экземпляр>/<набор>/<диск>.qcow2` — путь виден на карточке
   площадки. Первый раз уходит всё содержимое, дальше — только изменившиеся участки по 4 МиБ (qcow2 собирается
   с закреплённой раскладкой, файл разрежённый); после передачи файл сверяется целиком. При обрыве канала —
   повтор с места остановки; вручную — «Реплицировать сейчас» на закладке. Старые наборы на площадке удаляются,
   только если у площадки задан токен очистки. Узлу площадки нужна версия 0.9.1 или новее.

Файлы образов не шифруются (в канале — TLS): доступ к папке на сервере и к каталогу `images` на площадке —
как к самим данным машин.

## Репликация продукта на другие площадки

Закладка **«Репликация»** карточки продукта — куда ещё отправлять копии **этого** экземпляра. По умолчанию —
никуда. Отметьте площадку: отправка сразу настроена **«сразу после выполнения задания»** (после каждой
успешной копии); можно выбрать **«по расписанию»** (cron, например ночью). «Хранить на площадке» — сколько
копий держать там (пусто — как у продукта; удаление — только если у площадки задан токен очистки).
«Реплицировать сейчас» — вручную; рядом — итог последнего прохода и его журнал.

* **Зашифрованные копии** (все продукты, в том числе «Образ машины по SSH»): уходят снапшоты этого экземпляра и
  блоки, на которые они ссылаются, — как есть, сжатыми и зашифрованными; пароль репозитория не нужен, блоки,
  которые на площадке уже есть, не передаются; у PostgreSQL — и сегменты WAL. На площадке тот же репозиторий
  (тот же ключ и пароль): если его там нет, он создаётся сам; если под этим именем другой репозиторий —
  ошибка с подсказкой. Восстановление — «Мастер восстановления» → площадка-источник.
* **«Образы qcow2»**: на закладке — узлы HopeBackup, куда отправлять готовые qcow2 (только изменения).
  С 0.9.5 готовые qcow2 **никуда не отправляются, пока площадка не включена здесь явно**: площадки, перенесённые
  при обновлении из параметров 0.9.2 (или включённые без сохранения закладки), выключаются; в карточке продукта
  и в журнале сборки — уведомление «Репликация образов остановлена — включается на закладке «Репликация»».

**Репликация площадки целиком** («Площадки» → «Принимающие площадки»): репозиторий площадки копируется после
каждой копии и каждые N минут. На закладке продукта она показана отдельным блоком: принимающие площадки, время
последней синхронизации и попала ли туда последняя копия продукта. Переключатель **«Передавать этот продукт при
репликации площадки»** исключает продукт из неё: его снапшоты, блоки и сегменты WAL на принимающие площадки не
уходят, остальные продукты площадки — уходят (если на площадке есть исключённые продукты, репликация передаёт
снапшоты остальных и их недостающие блоки пачками, а не pack-файлы целиком; скорость — почти как у обычной, узлам
площадок нужна версия 0.9.5, со старым узлом блоки читаются по одному — медленнее на удалённых каналах). Если
исключение потом снять, уже переданные блоки повторно не передаются. По умолчанию исключён **«Образ машины по SSH»**
(образы большие и нужны обычно на одной площадке), остальные продукты передаются. Уже переданные копии
исключённого продукта на принимающей площадке остаются и удаляются по хранению. Отправить исключённый продукт на
нужную площадку — своей репликацией на этой же закладке. Если образ машины в итоге никуда не реплицируется,
в карточке продукта и в журнале копии — уведомление, где это включить (уведомление можно скрыть). Изменение
записывается в журнал аудита.

## Файлы, nginx, HAProxy, OpenVPN

Пресеты задают пути и команды проверки/применения. При восстановлении в `/` выполняется проверка
(`nginx -t`, `haproxy -c -f …`), применение (`systemctl reload …`) — только по флажку. Восстановление в другой
каталог — без проверок. Ключ CA OpenVPN попадает в копию: доступ к восстановлению ограничивайте ролями.

## Обновления

«Безопасность → Обновления» (только администратор). Новые версии ставятся из панели:

- **сервера** — архивом выпуска `hopebackup-<версия>-linux.tar.gz` для закрытого контура или онлайн по манифесту (каналы stable/beta, SHA-256 обязателен, автопроверка раз в сутки);
- **агентов** — кнопкой в блоке «Агенты»: агент скачивает свою сборку из комплекта сервера.

Как идёт установка:

1. Пакет проверяется: контрольные суммы, архитектура, пробный запуск `--version`.
2. Прежняя программа сохраняется (`hopebackup.prev`).
3. Ставится новая, служба перезапускается.
4. Если новая версия не ответила за 90 секунд (агент — не вышел на связь за 2 минуты), выполняется автоматический откат.

Итоги — в журнале аудита и уведомлениях (событие «Обновления»). Порядок для узлов управления, агентов и площадок, обновление скриптом и ручной откат — [07_Обновление.md](07_Обновление.md).

## Командная строка

```bash
hopebackup repo --url https://узел:8443 --token … --fingerprint … list           # снапшоты
HOPEBACKUP_PASSWORD=… hopebackup repo --url … show <снапшот>                     # потоки и доля новых блоков
HOPEBACKUP_PASSWORD=… hopebackup repo --url … backup --instance etc /etc         # разовая копия файлов
HOPEBACKUP_PASSWORD=… hopebackup repo --url … restore --instance etc --snapshot <id> --dest /tmp/etc
hopebackup node token --name agents-dc1 --role append                            # на узле
# площадка S3 и плагины без сервера управления:
HOPEBACKUP_PASSWORD=… hopebackup repo --url s3://бакет/hopebackup --s3-endpoint https://storage.yandexcloud.net \
  --s3-region ru-central1 --s3-access-key … --s3-secret-key … list
HOPEBACKUP_PASSWORD=… hopebackup repo --url … backup --plugin vault --instance vault --config '{"addr":"https://vault:8200","token":"…"}'
HOPEBACKUP_PASSWORD=… hopebackup repo --url … restore --plugin s3 --instance s3 --snapshot <id> --params '{"endpoint":"…","access_key":"…","secret_key":"…","target_bucket":"restored"}'
HOPEBACKUP_PASSWORD=… hopebackup repo --url … prune --keep-last 7 --dry-run          # очистка (токен администратора)
# облачный диск без сервера управления (параметры — как у площадки):
HOPEBACKUP_PASSWORD=… hopebackup repo --url cloud:// --cloud @nextcloud.json list
hopebackup inventory                                                               # опись этого сервера (JSON)
```

Репозиторий самодостаточен: при потере сервера управления копии восстанавливаются командной строкой
по адресу узла, токену и паролю репозитория.
