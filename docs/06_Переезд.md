# Переезд машин на другую платформу

Модуль «Переезд» переносит работающие Linux-машины на **Proxmox VE** и **zVirt / oVirt / РОСА Виртуализация**
с коротким простоем. Порядок работы:

1. Создаётся блочная реплика дисков.
2. Изменения синхронизируются, пока машина работает.
3. ВМ на цели проверяется тестовым запуском без сети.
4. Выполняется переключение: последняя синхронизация, выключение источника, запуск ВМ на цели.
5. До завершения переезда доступен откат.

Раздел панели: **Переезд → Проекты переезда**.

| Источник | Как читаются диски | Цель |
|---|---|---|
| Linux-машина с агентом: ВМ VMware, vCloud Director, Yandex Cloud, другие облака, «железо» | Агент на самой машине читает блочные устройства (O_DIRECT, в обход кэша). Драйверов ядра нет — обычная программа | Proxmox VE, zVirt / oVirt / РОСА |
| ВМ VMware vSphere без агента в гостевой ОС | Снимок ВМ → экспорт через vCenter/ESXi (VMDK streamOptimized) → разбор потока на агенте-сборщике | Proxmox VE, zVirt / oVirt / РОСА |

## Как это устроено

- **Реплика.**
  - Диски читаются блоками по 4 МиБ, у каждого блока считается сумма BLAKE3.
  - Первая синхронизация передаёт все непустые блоки. Следующие передают только блоки, сумма которых изменилась.
  - Цепочка синхронизаций хранится в обычном репозитории площадки (шифрование, дедупликация, принимающие площадки).
  - Старые звенья цепочки не удаляются, пока существует переезд.
- **Цель.**
  - Агент цели работает на узле Proxmox, а для zVirt/oVirt — на любой машине с доступом к Engine и узлам по imageio.
  - При первом применении агент создаёт ВМ с параметрами источника: vCPU, память, UEFI или BIOS, сетевые интерфейсы с **теми же MAC-адресами**.
  - Для дисков создаются тома, в них записываются блоки.
  - Дальше применяются только новые синхронизации.
  - Состояние (какая ВМ, какие тома, что уже применено) хранит сервер управления.
- **Переключение с агентом.**
  1. Останавливаются заданные службы (СУБД и т. п.).
  2. Файловые системы замораживаются (`fsfreeze`) на время последней синхронизации. Если агент не успеет, заморозку снимет отдельный страхующий процесс.
  3. Изменения применяются на цели.
  4. Источник выключается.
  5. ВМ на цели запускается.
- **Переключение без агента (vSphere).** Гостевая ОС выключается штатно через VMware Tools, затем выполняется последняя синхронизация выключенной ВМ.

## Подготовка

1. **Агенты.** Нужны два агента:
   - на переносимой машине (или любой агент-сборщик с доступом к vCenter — для источника без агента);
   - на стороне цели: на узле Proxmox VE или на машине с доступом к Engine zVirt/oVirt и его узлам (порт imageio 54322).

   Один агент может быть и тем и другим.
2. **Площадка.** Цепочка синхронизаций занимает примерно объём занятых блоков дисков плюс изменения за время переезда.
3. **Подготовка к KVM** — кнопка «Подготовка к KVM» в проекте. Её можно нажимать на работающей системе, повторно — безопасно.

   Что делает подготовка:
   - добавляет драйверы virtio в initramfs (dracut, initramfs-tools или mkinitcpio) — иначе ядро на новой платформе не найдёт корневой диск;
   - закрепляет имена сетевых интерфейсов за MAC-адресами (systemd `.link` и правило udev) — настройки сети применятся на новой платформе;
   - переписывает `/dev/sdX` в `fstab` на `UUID=`;
   - устанавливает `qemu-guest-agent`, если он есть в репозиториях.

   Изменённые файлы сохраняются рядом с суффиксом `.hb-prep`. Для источника без агента сценарий выполняется через гостевые операции vSphere: нужны пользователь гостевой ОС (root или с `sudo` без пароля) и работающие VMware Tools.

## Шаги в панели

| Шаг | Что происходит |
|---|---|
| **Новый переезд** | Выбираются источник, площадка, расписание синхронизаций (cron), цель: хранилище Proxmox или домен хранения zVirt, мост/профиль сети, имя ВМ, vCPU и память (пусто — как у источника) |
| **Синхронизировать** | Внеочередная синхронизация. При «Применять каждую синхронизацию» она сразу применяется на цели |
| **Применить на цели** | Применить последнюю синхронизацию. Первое применение создаёт ВМ и тома |
| **Тестовый запуск** | Снимок томов ВМ на цели. ВМ запускается **без сети**: интерфейсы отключены, потому что у ВМ те же адреса, что у работающего источника. Синхронизации продолжаются, применение откладывается |
| **Завершить тест** | ВМ останавливается, тома возвращаются к снимку, отложенное применение выполняется |
| **Переключить** | Последняя синхронизация при остановленных службах → применение → выключение источника → запуск ВМ на цели. Перед запуском делается снимок для отката. Расписание синхронизаций выключается |
| **Откат** | ВМ на цели останавливается, тома возвращаются к моменту переключения. Источник снова в работе: ВМ vSphere включается через vCenter, службы запускаются (если источник не выключался), иначе источник включают вручную. Синхронизации продолжаются |
| **Завершить переезд** | Снимок отката на цели удаляется, проект — «Завершён» |

Если хранилище цели не умеет снимки (толстый LVM в Proxmox), тестовый запуск и откат всё равно работают. После них тома помечаются «изменены на цели»: следующее применение обнулит их и запишет цепочку заново. Это дольше, но результат тот же.

## Цели

### Proxmox VE

- **Хранилища:** LVM, LVM-thin, ZFS, каталог (raw), NFS/CIFS, Ceph RBD (через `rbd map`).
- **Том на толстом LVM** перед первой записью обнуляется (BLKZEROOUT): такой том хранит старые данные.
- **ВМ:** `virtio-scsi-single`, диски `scsiN` с `discard` и `iothread`, интерфейсы `virtio` с MAC источника, `--agent enabled=1`.
- **UEFI:** `ovmf` + `q35` + `efidisk0`.
- **VMID:** следующий свободный в кластере, либо заданный в проекте.

### zVirt / oVirt / РОСА Виртуализация / HOSTVM

- ВМ из шаблона Blank, тип BIOS `q35_ovmf` или `q35_sea_bios`, интерфейсы `virtio` с MAC источника в выбранном профиле сети.
- **Диски:** raw, интерфейс `virtio_scsi`.
- **Файловый домен** (NFS, GlusterFS): разреженные диски.
- **Блочный домен** (iSCSI, FC): диски с полным выделением, которые перед записью обнуляются операцией `zero` в imageio.
- **Запись:** передачи imageio (`PUT` с `Content-Range`; нули — `PATCH zero`), по одной передаче на диск на всё применение.
- **Тест и откат:** снимки ВМ; интерфейсы отключаются флагом `linked=false`.

## Простой при переключении

Простой складывается из:

- остановки служб;
- последней синхронизации: чтения дисков источника и передачи изменений с прошлой синхронизации;
- применения этих изменений;
- загрузки ВМ.

Применение каждой синхронизации и частое расписание (например, `*/15 * * * *`) делают последнюю синхронизацию короткой.

Чтение дисков при каждой синхронизации — полное: изменения определяются сравнением сумм блоков, без драйверов и трассировки ядра. По сети и на площадку идут только изменённые блоки.

## Ограничения этой версии

- **Windows.** Гостевые Windows пока не переносятся. План: агент на VSS и драйверы virtio, подписанные производителем.
- **Платформы.** Цели OpenStack и OpenNebula/«Брест» — следующим шагом.
- **Yandex Cloud без агента.** Поддерживается только перенос с агентом в гостевой ОС.
- **Диски источника.** Их число и размер берутся из последней синхронизации. Увеличенный диск расширяется на цели сам. Уменьшение не поддерживается: такой диск читается заново.
- **Конфликт адресов.** Если выключение источника при переключении отключено, следите за конфликтом адресов: ВМ на цели запускается с теми же MAC.

## Командная строка (агент)

```sh
hopebackup action --plugin replica --name prepare-kvm          # подготовка к KVM на этой машине
hopebackup repo --url /mnt/repo backup --plugin replica --instance web01 --config '{"disks":["/dev/sda"]}'
hopebackup repo --url /mnt/repo backup --plugin replica --instance web01 --config '{"disks":["/dev/sda"]}' --kind cutover
hopebackup repo --url /mnt/repo restore --plugin replica --instance web01 --snapshot <id> \
    --params '{"platform":"proxmox","storage":"local-lvm","networks":{"*":"vmbr0"}}'
hopebackup action --plugin replica --name target-test-start --config '{"platform":"proxmox","state":{…}}'
```
