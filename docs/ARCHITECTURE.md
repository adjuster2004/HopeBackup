# HopeBackup — архитектура

## Роли и порты

Один бинарник `hopebackup` (Rust). Роль задаётся командой.

| Роль | Команда | Порт | Данные |
|---|---|---|---|
| Сервер управления | `hopebackup server` | 4443/tcp (HTTPS: панель, REST API, протокол агентов) | `/var/lib/hopebackup/server/` |
| Узел площадки | `hopebackup node run` | 8443/tcp (HTTPS: репозитории) | `/var/lib/hopebackup-node/` |
| Агент | `hopebackup agent run` | исходящие к серверу и площадке | `/var/lib/hopebackup/` (спул WAL, ключи туннелей) |
| archive_command | `hopebackup wal-push --spool DIR %p` | — | спул агента |
| restore_command | `hopebackup wal-fetch --job FILE %f %p` | исходящие к площадке | файл задания восстановления (0600) |
| Исполнитель на цели | `hopebackup restore-exec` (сервер запускает по SSH) | — | — |
| Без сервера | `hopebackup repo … list/show/backup/restore/prune` | исходящие к узлу или S3 | — |
| Уборка VPN | `hopebackup vpn-cleanup` (ExecStopPost служб) | — | `/run/hopebackup/vpn/` |

Данные копий идут **агент → площадка** напрямую (или через коннектор) и никогда не проходят через сервер
управления, кроме режима восстановления «через сервер» (обратный SSH-туннель).

## Модули (`hopebackup-core/src`)

| Модуль | Что делает |
|---|---|
| `store/` | Движок хранения. `crypto.rs` — ключи (мастер-ключ → ключи данных, идентификаторов, снапшотов, затравка FastCDC), `seal/open` (zstd если выгодно + XChaCha20‑Poly1305, AAD = идентификатор блока), обёртка мастер-ключа паролем (Argon2id). `repo.rs` — запись снапшота (FastCDC в отдельном потоке → пакетный `missing` → параллельное шифрование → pack-файлы 16 МиБ), чтение потока с проверкой каждого блока, объекты (сегменты WAL). `local.rs` — репозиторий в каталоге, индекс в памяти, атомарная запись, «только дописывание», очистка по политике. `http.rs` — тот же интерфейс к узлу по HTTPS с повторами. `s3.rs` — тот же репозиторий в любом хранилище объектов: бакет S3 или облачный диск (раскладка как на узле, кэш индекса и снапшотов на диске, блокировки записи `locks/`, Object Lock для S3). `prune.rs` — общая политика хранения |
| `cloud/` | `sigv4.rs` — подпись AWS Signature V4 (сверена с примерами AWS), `s3.rs` — клиент S3 (список v2, чтение диапазона, запись с Content-MD5, многочастная загрузка, Object Lock, классы хранения); `objstore.rs` — общий интерфейс хранилища объектов (повторы при 429/5xx); `webdav.rs` (Nextcloud, ownCloud), `yadisk.rs` (REST API Яндекс Диска), `gdrive.rs` (Drive API v3, плоская папка), `oauth.rs` (вход по коду устройства, обновление токенов), `drive.rs` (параметры облачной площадки) |
| `node/` | Узел площадки (axum): токены `read` / `append` / `admin` (на узле — только SHA-256 токенов), несколько репозиториев, очистка только с `admin` |
| `plugins/` | Контракт `Plugin` (discover / backup / restore / action) и каталог продуктов. `postgres.rs` — PostgreSQL 14+ и форки (установка PGDG на чистую ВМ); `files.rs` — файлы с пресетами nginx/HAProxy/OpenVPN; `host/` — «Сервер Linux целиком» (`system.rs` — ОС, ядро, загрузка, железо, диски, сеть, безопасность; `analysis.rs` — анализ и рекомендации; `inventory.rs` — опись процессов, расписаний, служб, монтирований, Docker, пользователей, портов, пакетов; `mod.rs` — копия по частям и восстановление пользователей и файлов); `gitlab.rs` — Omnibus/Docker, `gitlab-backup` без сжатия + секреты; `vault.rs` — снапшот raft потоком; `s3bucket.rs` — бакеты S3 (tar на бакет + метаданные); `tarsniff.rs` — прозрачный разбор tar-потока (backup_label, backup_manifest) без временных файлов; `appkit.rs` — общее для приложений (команды от пользователя продукта или в контейнере, поток вывода утилиты в репозиторий и обратно, секреты во временных файлах, службы systemd/OpenRC, разбор юнитов, tar с xattr, распаковка с владельцем); `hope.rs` — продукты Hope и движок «раскладки» (части с фазами: при остановке / на ходу, замена при восстановлении), на нём же Jenkins, Nexus, Keycloak; `mysql.rs`, `mssql.rs`, `mongodb.rs`, `redis.rs`, `clickhouse.rs` — СУБД; `ldap.rs`, `docker.rs`, `kube.rs`, `monitoring.rs` (Zabbix, Grafana), `opensearch.rs`, `nexus.rs` (Nexus, Harbor); `vm/` — образы ВМ (`libvirt.rs`, `proxmox.rs`, `ovirt.rs`, `opennebula.rs`, `openstack.rs`, `vmware.rs` — SOAP и NFC, `xen.rs` — XAPI, `nutanix.rs`, `restapi.rs` — SpaceVM и VMmanager, `xml.rs` — разбор XML и XML-RPC) |
| `connectors/` | Коннекторы к площадке: `direct`, `ssh.rs` (системный OpenSSH, `-L`, jump-хост, переподключение, `known_hosts` агента), `openvpn.rs` (профиль по белому списку директив, `--script-security 1`, `--route-nopull`), `wireguard.rs` (ядро или wireguard-go/boringtun), `ipsec.rs` (strongSwan swanctl: L2TP/IPsec со своим xl2tpd/pppd, IKEv2 PSK/EAP), `net.rs` (интерфейсы `hb*`, маршруты только до площадки, файл владения канала для агента и сервера на одной машине). `TunnelManager` держит по слоту на коннектор и переподнимает канал при смене параметров. Площадка пробует коннекторы по приоритету, проверяя узел (`/v1/health` с закреплённым сертификатом) |
| `agent/` | Агент: подключение по одноразовому токену, длинный опрос сервера, выполнение заданий с потоковой передачей журнала, непрерывная отправка WAL из спула |
| `exec.rs` | Исполнитель заданий — один для агента, сервера и `restore-exec` |
| `fssnap.rs` | Снимки ФС перед файловой копией: по `/proc/self/mountinfo` находит тома под путями копии, снимает LVM (обычные и thin), ZFS, btrfs, монтирует только для чтения в `/run/hopebackup/snap/<задание>/`, проверяет переполнение снимка LVM, удаляет снимки (`Drop`) и убирает оставшиеся от прерванных копий. Чтение из снимка — через подмену путей (`files::Remap`): в tar пишутся исходные пути |
| `sshc.rs` | Клиент SSH (russh): пароль, keyboard-interactive, ключ; закреплённый отпечаток ключа хоста; команды, файлы, sudo без пароля или с паролем через stdin |
| `dist.rs` | Комплект сборок для машин (x86_64/aarch64 × glibc/musl): поиск, распаковка, выбор по `uname -m` и библиотеке C машины |
| `exclude.rs` | Исключения: шаблоны путей и имён (`*`, `**`, `?`), общий список сервера + список экземпляра, предел размера файла |
| `server/` | Сервер управления: `state.rs` (состояние в `state.json`, 0600), `jobs.rs` (очередь, журналы, история), `auth.rs` (PBKDF2, HMAC-сеансы, права из метода и пути — новые обработчики защищены по умолчанию), `api.rs` (REST API панели, `docs/API.md`), `agent_api.rs`, `ssh_restore.rs` (восстановление по SSH), `vm/` (новая ВМ для восстановления: Proxmox VE, VMware vSphere, Yandex Compute, AWS EC2), `replication.rs` (принимающие площадки), `cluster.rs` (принимающие узлы управления), `machines.rs` (серверы и ВМ по SSH: опись, анализ, установка агента, экземпляры по рекомендациям), `disk.rs` (встроенный узел для площадки «диск сервера», `/node/<id>`), `cloudauth.rs` (вход в облака, продление токенов), `mail.rs` (SMTP, раздел «Почта и уведомления»), `notify.rs` (события, монитор состояний, журнал), `recovery.rs` (ссылка сброса пароля, аварийный токен вендора), `retry.rs` (повторы неудачных копий, сверка потерянных итогов с площадкой, догон пропущенных запусков), расписания cron |
| `tlsutil.rs` | Самоподписанные сертификаты (rcgen), клиент с закреплённым отпечатком SHA-256 (rustls), определение отпечатка при первом подключении |

## Репозиторий на площадке

```
repos/<имя>/config.json          открытая конфигурация; мастер-ключ зашифрован паролем (Argon2id)
repos/<имя>/packs/ab/<id>.pack   зашифрованные блоки подряд; id = BLAKE3 содержимого pack-файла
repos/<имя>/index/<id>.json      блок → (pack, смещение, длина); идентификаторы — keyed BLAKE3
repos/<имя>/snapshots/<id>.json  открытый заголовок (экземпляр, вид, время, начало WAL) + список ссылок + зашифрованное тело
repos/<имя>/objects/wal/<экз>/   сегменты WAL (сжаты и зашифрованы, AAD = имя сегмента)
```

* Идентификатор блока — BLAKE3 с ключом репозитория: площадка не может проверить догадку о содержимом.
  Границы блоков FastCDC тоже зависят от ключа (затравка gear-хэша).
* Узел видит заголовки снапшотов и списки ссылок — этого хватает для политики хранения и сборки мусора
  без ключа. Размеры блоков при этом видны (известное и принятое ограничение).
* Запись — только новых файлов (атомарно: временный файл, fsync, переименование). Повторная запись того же
  содержимого — не ошибка (повторы после обрыва связи).
* Очистка: оставляет N последних копий каждого вида для каждого экземпляра (у экземпляра своё N),
  удаляет pack-файлы без живых блоков и сегменты WAL старше начала самой старой оставшейся полной копии.
  Pack-файлы, чьи блоки недавно признаны существующими, сутки не трогаются — на них может ссылаться
  копия, которая ещё пишется.

Площадка S3 устроена так же (`<префикс>/<репозиторий>/…` + `locks/`). Агенты пишут ключом без права
удаления; очистку выполняет сервер ключом администратора. Пока есть свежая (30 мин) чужая блокировка записи,
pack-файлы не удаляются; перед удалением список снапшотов и блокировок проверяется второй раз, индекс
удаляется раньше pack-файла, а нечитаемый снапшот останавливает очистку.

## Коннекторы VPN

Канал поднимается от root на время работы агента/сервера. В туннель направляется только узел площадки (`/32`)
или явно заданные сети (не шире `/8` и не накрывая шлюз по умолчанию); маршруты, DNS и `redirect-gateway`
от сервера VPN игнорируются. Интерфейс — `hb` + 8 символов идентификатора коннектора; файл
`/run/hopebackup/vpn/<iface>.pid` позволяет агенту и серверу на одной машине пользоваться одним каналом.
Параметры, попадающие в файлы настроек (PSK, логины, адрес WireGuard), проверяются на управляющие символы.

## Новая ВМ для восстановления (`server/vm/`)

Создать ВМ у провайдера → одноразовый ключ ed25519 и пользователь `hopebackup` через cloud-init → ожидание
SSH и `cloud-init status --wait` → `prepare_script` → обычное восстановление по SSH → цель «сервер по SSH».
При сбое ВМ удаляется. Proxmox — API-токен (клон, ресурсы, адрес через guest agent); VMware — REST `/api`
(клон ВМ или шаблон библиотеки, спецификация настройки с cloud-init); Yandex — IAM по JWT PS256 сервисного
аккаунта, Compute/VPC; AWS — EC2 Query API с SigV4.

## Принимающие площадки и узлы управления

* **Репликация площадок** (`replication.rs`): после каждой копии и периодически — конфигурация, pack-файлы
  (только с индексом, с проверкой BLAKE3), снапшоты (чьи блоки уже доехали), объекты. Перед передачей pack-файла —
  его индекс (без данных) и проверка блоков на принимающей: все уже есть (их перенесла репликация с исключениями
  или репликация продукта под другими pack-файлами) — файл пропускается и запоминается по паре площадок; часть —
  передаются только недостающие блоки. Если на площадке есть продукты, исключённые из её репликации, — снапшоты
  остальных и их недостающие блоки: пачками до 256 блоков (`POST /v1/r/:repo/blobs`, у узла старше 0.9.5 — по
  одному), до трёх пачек одновременно, сборка pack-файлов с отправкой в фоне (до двух). Замер —
  `server/repl_bench.rs` (`BENCH_MB=512 cargo test repl_bench -- --ignored --nocapture`). Удаления не
  зеркалируются; очистка принимающей площадки — по политикам всех экземпляров каталога, копии моложе 7 дней
  и копии неизвестных экземпляров не удаляются.
* **Каналы до площадок** (`connectors/mod.rs`): один канал на коннектор, подъём и проверка под замком коннектора —
  параллельные задания (репликация площадки и продуктов, отправка образов, копии) не поднимают канал вторично:
  проверенный за последние 15 с канал берётся без повторной проверки; не ответивший канал перепроверяется через
  3 с и только потом переподнимается — чтобы не рвать канал, по которому идёт передача у других заданий.
* **Кластер** (`cluster.rs`): приглашение одноразовым кодом; активный узел рассылает каталог раз в 30 с и при
  изменениях (HMAC, метка времени и версия против повторов); эпохи: «Принять управление» опрашивает
  остальные узлы и ставит эпоху max + 1, устаревший активный узел становится принимающим. Принимающий узел
  не меняет каталог и не запускает задания (409). Агенты получают список серверов и эпоху и переключаются
  сами (3 сбоя подряд, 409 или устаревшая эпоха).

## PostgreSQL 14+ и qdatabase

1. **Обнаружение**: каталог бинарников — из настроек, запущенного процесса `postgres` или стандартных мест
   (`/usr/lib/postgresql/*/bin`, `/usr/pgsql-*/bin`, `/opt/qdatabase-*/bin`); версия — `postgres --version`;
   форк (`qdatabase`) — по пути и строке версии; параметры сервера — через `psql` из того же каталога.
   Утилиты запускаются от пользователя ОС СУБД с его дополнительными группами (как `su`).
2. **Архив WAL** (действие `setup-wal`): `archive_mode = on`, `archive_command = hopebackup wal-push --spool …`,
   `archive_timeout = 60s`. `wal-push` только кладёт сегмент в локальный спул (fsync + rename) — медленный
   канал не тормозит СУБД; агент отправляет спул на площадку.
3. **Полная копия**: `pg_basebackup -D - -Ft -X none` — tar-поток прямо в движок хранения. Из потока по дороге
   берутся `backup_label` (начало WAL) и `backup_manifest` (конец WAL). Конфигурация вне каталога данных
   (Debian/Ubuntu: `/etc/postgresql/…`) сохраняется отдельным потоком `config.tar`. Дополнительно — `pg_dump -Fc`
   выбранных баз.
4. **Восстановление**: проверка, что на цели та же мажорная версия и тот же форк; распаковка в пустой
   каталог; конфигурация из `config.tar` (пути на старый каталог закомментированы, SSL выключается, если
   на цели нет сертификатов); `restore_command = hopebackup wal-fetch …`, `recovery_target_time`,
   `recovery_target_action = promote`, `archive_mode = off` (восстановленный сервер не пишет в репозиторий
   продуктива); запуск, ожидание выхода из восстановления, затем доступ к площадке убирается из конфигурации,
   файл задания удаляется.

## Приложения, СУБД и образы ВМ (0.7)

* **Поток без временных файлов**: вывод утилиты (`mysqldump`, `mariabackup --stream`, `mongodump --archive`,
  `redis-cli --rdb -`, `vzdump --stdout`, `slapcat`, `pg_dumpall`) идёт прямо в нарезку и шифрование; при
  восстановлении поток из репозитория — в stdin утилиты (`mysql`, `mbstream`, `mongorestore`, `qmrestore -`).
  Там, где продукт пишет только файл (`BACKUP DATABASE` SQL Server, `ipa-backup`, ClickHouse `BACKUP`), файл
  читается сразу после записи и удаляется. Образы дисков с API платформ (imageio, Glance, NFC vSphere, XAPI
  `/export`, Prism) — потоком HTTP, загрузка — телом запроса из потока репозитория. Узлы по SSH — каналами
  russh в обе стороны (sudo — паролем в начале stdin).
* **Секреты** — во временных файлах 0600 в `/run/hopebackup/tmp` (`--defaults-extra-file`, YAML `--config`,
  XML `--config-file`, `.pgpass`, сценарий mongosh) или в окружении; в контейнере — файлом внутри контейнера
  (`docker exec -i … cat >`), удаляется после задания; `docker exec -e ИМЯ` берёт значение из окружения
  клиента docker, а не из командной строки.
* **Цепочки журнала**: MySQL — позиция binlog из заголовка дампа (`--master-data=2`) или
  `xtrabackup_binlog_info`, архив — закрытые файлы после `FLUSH BINARY LOGS`; MS SQL — LSN из
  `msdb.dbo.backupset`, цепочка восстановления строится по копиям экземпляра (полная → последняя разностная →
  журналы). Очистка хранит копии журнала, пока хранится полная копия, с которой начинается их цепочка
  (`store/prune.rs`, виды `binlog` и `incr`).
* **Образы ВМ**: libvirt — внешний снимок `--disk-only --atomic` (с `--quiesce`, если есть агент гостя), слои
  qcow2 копируются по отдельности (`qemu-img info --backing-chain`), затем `blockcommit --shallow --active
  --pivot` и удаление оверлея; восстановление собирает цепочку `qemu-img rebase -u`. vSphere — SOAP
  (RetrievePropertiesEx, CreateSnapshot_Task, ExportSnapshot/HttpNfcLease с продлением, CreateDescriptor,
  CreateImportSpec/ImportVApp), CBT — QueryChangedDiskAreas с changeId прошлой копии (только учёт).

## Переезд (0.8)

* **Реплика** (`plugins/replica.rs`): диск читается с O_DIRECT (данные ФС пишутся мимо страничного кэша
  устройства — обычное чтение вернуло бы устаревшие страницы), блоками 4 МиБ; карта `<диск>.map` — 16 байт
  BLAKE3 на блок (нулевой блок — нули), поток `<диск>.delta` — `HBDELTA1`, размер, затем записи
  «смещение u64, длина u32, вид u8» (0 — данные, 1 — нули). Синхронизация сравнивает суммы с картой прошлой
  — драйверов и трассировки ядра нет. Переключение (`--kind cutover`): остановка служб, `sync`, `fsfreeze`
  смонтированных ФС этих дисков (корень последним) под страховкой `setsid sh -c "sleep T; fsfreeze -u …"`.
* **Без агента** (`replica_vs.rs`, `vmdk.rs`): снимок vSphere → ExportSnapshot → поток VMDK streamOptimized
  (маркеры зёрен zlib, метаданные пропускаются, промежутки — нули) → тот же `scan`. Подготовка гостевой ОС —
  InitiateFileTransferToGuest / StartProgramInGuest / ListProcessesInGuest / InitiateFileTransferFromGuest.
* **Цели** (`plugins/migrate.rs`, трейт `Target`: `open` → тома, `close` → состояние, `power` — тест,
  запуск, откат): Proxmox — `qm create`/`pvesm alloc`/`pvesm path` (RBD — `rbd map`), запись прямо в том;
  oVirt — API Engine и imageio (`PUT` + `Content-Range`, `PATCH zero/flush`). Новый том толстого LVM или
  блочного домена обнуляется целиком (BLKZEROOUT / `zero`). Снимки для теста и отката; без снимков —
  `state.dirty`: следующее применение обнуляет тома и пишет цепочку с первой синхронизации.
* **Сервер** (`server/migration.rs`): сущность `Migration` в каталоге, шаги — обычные задания агентов
  (backup / restore / action `target-*`, `poweroff`, `resume`), следующий шаг решает `on_job_finished` по итогу
  задания: синхронизация → (авто)применение; переключение → применение → выключение источника → запуск;
  применение во время теста откладывается. Цепочка реплики не очищается (`after_backup` пропускает её).
* **Поток репозитория** (`Repo::restore_stream`): канал tokio и ожидание потока записи через
  `spawn_blocking` — блокирующий `join` в рабочем потоке рантайма мог заблокировать получателя, который сам
  ждёт задач рантайма (запись в imageio).

## Сервер ↔ агент

* Подключение: одноразовый токен (24 ч) из панели + отпечаток сертификата сервера → постоянный токен агента.
* Длинный опрос `/api/agent/poll` (до 25 с): агент сообщает версию и состояние спулов WAL, получает задания и
  список экземпляров для отправки WAL (с доступом к площадке). Секреты передаются только по TLS с закреплённым
  сертификатом и не пишутся агентом на диск, кроме ключей SSH-туннелей (0600).
* Журнал задания отправляется раз в секунду; итог — `/finish`. После успешной копии сервер запускает очистку
  площадки по политикам хранения (если задан токен администратора узла).

## Устойчивость к обрывам (0.6)

* **Снапшот — последним.** Pack-файлы пишутся атомарно (временный файл → переименование), снапшот — только после
  всех данных, узел проверяет, что все блоки снапшота существуют. Оборванная копия не создаёт точки восстановления;
  её блоки уже в репозитории и при повторе не передаются (`missing`). Сборка мусора не трогает pack-файлы
  моложе часа. В `extra` снапшота — `job` (id задания).
* **Outbox агента.** Итог задания (`{ok, result|error, log}`) сначала пишется в `outbox/<задание>.json` (0600), затем
  отправляется (6 попыток); не доставленные уходят в начале каждого цикла опроса. В отчёте агента — `pending`
  (итоги в outbox) и `started` (время запуска процесса).
* **Сервер.** После перезапуска задания, выполнявшиеся у агентов, ждут отчёта 15 минут (`await_until`), задания
  самого сервера и не начатые — прерванные. По отчёту агента (`fail_stale`): задание не в `running` и не в
  `pending` — прервано (сразу, если агент запущен позже начала задания; иначе через минуту). Поздний итог
  принимается и для прерванного задания. «Принять управление» на принимающем узле тоже даёт 15 минут.
* **Терпение к сети.** Запросы к узлу (`store/http.rs`) и к хранилищам объектов (`cloud/objstore.rs`) повторяются
  с паузами 1, 2, 4 … 30 с до предела: 10 минут у агента и `restore-exec`, 30 с у сервера (панель не должна висеть).
* **Повторы (`server/retry.rs`).** Раз в 30 с: для завершённых с ошибкой повторяемых заданий (`schedule`, `retry`,
  `catchup`, `manual_retry`) назначает `retry_at` по политике экземпляра или сервера, при исчерпании — письмо
  `backup_failed_final`. В срок: есть более свежая успешная копия — повтор не нужен; задание прервано — ищет на
  площадке снапшот с `job` = id задания (сверка); иначе ставит копию с `attempt + 1`. Догон: для каждого
  расписания находит последний пропущенный запуск после последнего задания этого вида (`missed_since`) в окне
  `catch_up_hours`.
* **Память узла (0.6.1).** Индекс блоков — `store/cindex.rs`: отсортированный массив записей по 44 байта
  (идентификатор, номер pack-файла, смещение, длина) и небольшая хэш-таблица новых записей, вливаемая в массив
  слиянием на месте. Заголовки снапшотов — в `heads/<id>.json` и в памяти (для старых репозиториев создаются
  при открытии разбором записи). Запись снапшота разбирается потоком (`store/snapfile.rs`): заголовок, ссылки
  по одной, тело пропускается. Очистка: план по заголовкам → битовая карта живых блоков по номерам в индексе
  (ссылки оставляемых снапшотов читаются из файлов по одному) → для каждого pack-файла «есть живые / есть
  мёртвые». Узел принимает запись снапшота потоком во временный файл и отдаёт потоком из файла. S3 и облачные
  диски: тот же индекс; заголовки и ссылки точек (32 байта на блок) кэшируются на диске сервера после первого
  чтения. pack-файлы передаются как `Bytes`, без копий.
* **Задания на сервере.** В памяти — не больше 2000 заданий и журналы только выполняющихся; журнал
  завершённого задания читается из `jobs/<id>.json` по запросу и возвращается в память на время изменения.
* **Уборка.** Снимки ФС — при запуске агента и перед каждой файловой копией (кроме снимков идущих копий);
  временные каталоги описи и установки на машинах (`hopebackup.XXXXXX` старше часа) — при следующем SSH-заходе.

## Восстановление по SSH

Сервер проверяет цель (вход по ключу, root или `sudo -n`), копирует свой бинарник в
`/usr/local/bin/hopebackup`, запускает `hopebackup restore-exec` и передаёт задание через stdin (секреты не
попадают в командную строку). В режиме «через сервер» в ту же SSH-сессию добавляется `-R` до площадки, и цель
читает данные с `127.0.0.1:<порт>`. Вывод исполнителя — JSON-строки (журнал, итог, ошибка).

## Серверы и ВМ по SSH

Сервер управления подключается к машине своим клиентом SSH (без внешнего ssh): пароль (password и
keyboard-interactive) или ключ; отпечаток ключа хоста закрепляется при первом подключении. Вход и определение прав —
не дольше 90 с, каждая команда — со своим пределом времени на всё (канал, stdin, вывод), вывод — не больше 64 МБ.
Права root — вход под root, `sudo -n` или `sudo -k -S` (пароль первой строкой stdin; `-k` — всегда спрашивать,
чтобы закэшированные права не оставили пароль в данных команды). Опись: программа сервера (та же сборка,
glibc ≥ 2.17) пишется от root в `mktemp -d` root (/var/tmp → /tmp → /dev/shm → /root → /run; каталоги noexec
пропускаются), сверяется SHA-256, запускается `hopebackup inventory`, каталог удаляется; ответ — JSON описи (секреты
скрываются до записи на диск). Без root — то же от пользователя. Иначе — сценарий sh (`SHELL_INV`). Внешние
команды описи — с пределом времени и без унаследованного stdout. Анализ считается на сервере по описи и наличию
агента. Установка агента — та же программа в /opt/hopebackup, `agent enroll --token-file` с одноразовым токеном
(1 ч, привязан к машине: агента к ней привязывает обработчик `enroll`; неиспользованный токен отзывается), юнит
systemd или сценарий OpenRC.

Цели восстановления по SSH с паролем используют системный ssh: пароль отдаёт сама программа как `SSH_ASKPASS`
(пароль — в файле 0600, в окружении только путь; процесс без управляющего терминала). Перед работой `sudo -n true`
определяет, нужен ли пароль sudo; адрес передаётся после `--`, пользователь и адрес проверяются.

## Сборки и комплект (`dist.rs`)

Четыре сборки одного кода: `x86_64-gnu` и `aarch64-gnu` (glibc ≥ 2.17, `cargo zigbuild --target
<арх>-unknown-linux-gnu.2.17`) и `x86_64-musl`, `aarch64-musl` (статические, `-C target-feature=+crt-static`,
libc и crt — от zig). Стандартная библиотека для ARM и musl собирается из исходников (`-Zbuild-std`), так что
нужен только компилятор хоста и исходники `library/` той же версии Rust. Сервер ищет сборки в
`$HOPEBACKUP_DIST`, `<каталог программы>/dist`, `/opt/hopebackup/dist`, `<данные>/dist` (файлы
`hopebackup-<арх>-<libc>[.gz]`), для машины выполняет `dist::PROBE` (`uname -m`, `getconf GNU_LIBC_VERSION`,
`ldd --version`, `/lib/ld-musl-*`) и берёт `gnu` при glibc ≥ 2.17, иначе `musl`.

## Почта, уведомления, восстановление доступа

`server/mail.rs` — SMTP (lettre, rustls; корни Mozilla, системные и свой ЦС), раздел панели. `server/notify.rs` —
каталог событий, очередь отправки (не блокирует источник), предел 20 писем в час на событие, журнал; источники:
`Jobs::finish` (копирование, восстановление, прочие задания), вход (подбор пароля), опись по SSH (ключ хоста),
«Принять управление»; монитор раз в минуту (активный узел: агенты по связи в памяти — идёт ли длинный опрос,
RPO через `instance_view`, WAL, место, принимающие узлы; принимающий узел — давность каталога от активного).
Переходы через порог помнятся в `notify_state.json`. `server/recovery.rs` — ссылки сброса (в каталоге — SHA-256
токена, 30 минут, одноразовые), аварийный токен вендора (RS256, вшитый открытый ключ лицензий HopeDFS;
`--features testkey` подставляет тестовый ключ из `HOPEBACKUP_TEST_VENDOR_PUBKEY` для `tests/notify.sh`),
отпечаток — machine-id как у лицензий HopeDFS. Сеансы панели: `user|поколение|срок` с HMAC; поколение
увеличивается при смене и сбросе пароля.

## Облачные диски

Репозиторий в облачном диске устроен так же, как в S3 (`<папка>/<репозиторий>/packs|index|snapshots|objects|locks`):
WebDAV и Яндекс Диск — каталогами, Google Диск — файлами в одной папке с путём в имени (имена в Google Диске не
уникальны, папки создавались бы гонками при записи с нескольких агентов). Время изменения для блокировок и
«молодых» pack-файлов — из облака. Агенты Google обновляют токен доступа сами (токен обновления не меняется);
токен Яндекса раздаётся агентам, сервер продлевает его заранее. Вход OAuth выполняет сервер: панель получает
только код для пользователя и идентификатор входа.

## Ограничения

* Нарезка по содержимому на вырожденных (почти периодических) данных режет блоки по максимальному размеру —
  дедупликация таких данных хуже. Реальные таблицы этим не страдают.
* Физическая копия PostgreSQL — полная (дедупликация экономит канал, но читается весь кластер); настоящие
  инкременты (pgBackRest / `pg_basebackup --incremental` в PG17+) — следующий этап.
* Табличные пространства вне каталога данных в tar-потоке `pg_basebackup -D -` не поддерживаются.
* Индекс репозитория узел держит в памяти: 44 байта на блок (≈40 МБ на 1 ТБ уникальных данных); при открытии
  читаются все файлы `index/` (≈2 с на 1,6 млн блоков).
* Плагины встроены в бинарник; внешние плагины (отдельные процессы) — следующий этап.
* Образы ВМ: читается весь диск (дедупликация экономит место и канал до площадки, но не чтение); чтение
  только изменённых блоков (VDDK для vSphere, инкрементальные копии oVirt/Proxmox Backup Server) — следующий
  этап. SpaceVM и VMmanager восстанавливаются файлами на узел (импорт — средствами платформы).
* Проверено на настоящих продуктах: MariaDB 10.11, Redis 7, OpenLDAP 2.6, libvirt 10 / QEMU 8, etcd 3.4,
  SQLite (Grafana). MS SQL Server, MongoDB, ClickHouse, Keycloak, FreeIPA, Docker, Kubernetes, OpenSearch,
  Harbor, Proxmox VE, oVirt, OpenStack, vSphere, XCP-ng, Nutanix, SpaceVM, VMmanager, OpenNebula — по
  документированным API и CLI на имитациях (`tests/dbms_mocks.sh`, `tests/apps.sh`, `tests/vm.sh`).
* Облачные диски медленнее S3 и ограничивают частоту запросов; список Google Диска читается целиком
  (около 130 запросов на репозиторий в 1 ТБ). Защиты от удаления (Object Lock) у них нет.
* Опись «сервера целиком» видит то, что работает и запускается сейчас; программы, запускаемые вручную, нужно
  указать в «Дополнительных путях». Память процессов не сохраняется.
* Снимки ФС: LVM, ZFS, btrfs. XFS/ext4 без LVM, Stratis, VDO, снимки гипервизора — копия «на ходу» (или
  `pre_snapshot` с остановкой записи). Снимок LVM thick требует свободного места в группе томов; переполненный
  снимок обнаруживается после копии (копия — ошибка, повтор).
* Блокировки записи S3 — по времени (30 мин, обновляются каждые 5 мин): агент, «замёрзший» дольше 30 мин
  посреди записи, может застать удалённые очисткой блоки — такая копия завершится ошибкой проверки ссылок
  снапшота, данные прежних копий не страдают.
