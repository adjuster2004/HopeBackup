# HopeBackup — установка

## 1. Что где ставится

| Роль | Где | Требования |
|---|---|---|
| Узел площадки | Linux-сервер на резервной площадке (или в облаке) | x86_64 или ARM64, диск под копии, порт 8443/tcp доступен агентам (или через SSH-туннель) |
| Сервер управления | Linux-сервер основной площадки | x86_64 или ARM64, порт 4443/tcp для администраторов и агентов, клиент OpenSSH (туннели, восстановление по SSH); исходящая почта (SMTP) — для уведомлений и ссылок сброса пароля |
| Агент | Каждый хост с продуктом (СУБД, nginx…) | x86_64 или ARM64, клиент OpenSSH (если коннектор — SSH-туннель), исходящий доступ к серверу и площадке |
| Цель восстановления по SSH | Любой Linux-сервер | вход по ключу или паролю под root или пользователем с `sudo` (без пароля или с паролем); для PostgreSQL — установленный PostgreSQL той же мажорной версии (или qdatabase той же сборки) |

Поддерживаемые ОС — x86_64 и ARM64 (aarch64):

| Сборка | Где работает |
|---|---|
| `x86_64-gnu`, `aarch64-gnu` (glibc ≥ 2.17) | CentOS/RHEL/Oracle 7+, Alma/Rocky 8+, РЕД ОС 7+, Debian 8+, Ubuntu 14.04+, SLES/openSUSE 12+, Astra Linux 1.6+, ALT 8+, МСВСфера, Fedora, Arch, Gentoo; на ARM — Ubuntu/Debian/RHEL для ARM64, Raspberry Pi OS 64-bit, AWS Graviton, Huawei Kunpeng, Baikal-M |
| `x86_64-musl`, `aarch64-musl` (статические, без библиотек) | **Alpine без gcompat**, системы с glibc старше 2.17 (CentOS 6), минимальные образы и контейнеры — любой Linux этой архитектуры |

Установка и сервер управления выбирают сборку сами: glibc ≥ 2.17 — сборка `gnu` (быстрее), иначе статическая
`musl`. На Alpine службы ставятся в OpenRC. 32-битные ARM (armv7) и другие архитектуры — только сокращённая
опись по SSH командами sh.

### Сколько ресурсов давать

Шифрует и сжимает агент; узел площадки только проверяет контрольные суммы pack-файлов и пишет их на диск.
Поэтому узлу нужны прежде всего **диск** и **сеть**, памяти и процессора — немного.

**Узел площадки** (защищаемые данные — объём источников; 30 ежедневных точек, ~3% изменений в день):

| Защищаемых данных | vCPU | ОЗУ | Диск под копии |
|---|---|---|---|
| до 1 ТБ | 1–2 | 512 МБ | 1,5–2 ТБ |
| 1–5 ТБ | 2 | 1 ГБ | 1,5–2× данных |
| 5–20 ТБ | 2–4 | 2–4 ГБ | 1,5–2× данных |
| 20–50 ТБ | 4 | 4–8 ГБ | 1,5–2× данных |

* **Память.** Индекс блоков — около 44 байт на блок (≈80 МБ на 1 ТБ защищаемых данных при 30 точках);
  список точек — из заголовков, очистка — битовая карта живых блоков (1 бит на блок), записи снапшотов в
  память не читаются. Замер на репозитории «1 ТБ, 30 точек» (1,6 млн блоков): около 100 МБ после открытия,
  пик 121 МБ (при открытии; очистка его не поднимает); список точек — 0,02 с, очистка — 8–9 с, открытие —
  от 2 с до 20 с в зависимости от кэша диска. Остальная память — кэш
  файловой системы ядра: чем больше, тем быстрее восстановление.
* **Диск.** Первая копия после сжатия + изменения × число точек + 20–25% запаса. Базы и тексты сжимаются в
  2–3 раза, архивы и медиа — почти никак. Пример: 1 ТБ, сжатие до 60%, 3% изменений в день, 30 точек —
  0,6 + 0,54 ≈ 1,14 ТБ, с запасом ≈ 1,5 ТБ. Для PostgreSQL добавьте WAL за срок хранения. Pack-файлы пишутся
  последовательно по 16 МиБ — подходят HDD; лучше RAID или ZFS и не на хранилище продуктива. Служебные
  данные: ≈95 МБ на точку на 1 ТБ источника и ≈110 байт индекса на блок.
* **Процессор.** Проверка BLAKE3 и TLS: 2 vCPU — около 1 Гбит/с; 1 vCPU — до ~300 Мбит/с.
* **Сеть** — обычно главное ограничение: первая копия 1 ТБ — около 2,5 ч на 1 Гбит/с и около 23 ч на
  100 Мбит/с; дальше по сети идут только изменения, они должны укладываться в окно копий.

**Сервер управления:** 1–2 vCPU, 512 МБ – 1 ГБ ОЗУ, 10–20 ГБ диска (без заданий — около 15 МБ памяти). Если у
него есть площадка «диск сервера» — добавьте ресурсы узла по таблице выше; для площадок S3 и облачных дисков
он при очистке держит индекс репозитория (те же ≈80 МБ на 1 ТБ) и кэширует ссылки точек на диске
(32 байта на блок на точку).

**Агент:** до ~150 МБ памяти во время копии (пакет блоков до 32 МиБ, его шифротекст, pack-файл 16 МиБ) —
после задания память возвращается системе; в покое — 15–30 МБ; одно ядро загружается на время копии. Диск: программа ~25 МБ; для PostgreSQL —
место под очередь WAL на время недоступности площадки (≥5 ГБ). Что донастроить на конкретной ВМ, подсказывает
анализ машины («Подготовка машины»).

## 2. Установка с Windows (PuTTY)

Положите `plink.exe` и `pscp.exe` в `C:\HopeBackup\tools\PuTTY` (или используйте `C:\HopeDFS\tools\PuTTY`).

```bat
:: узел площадки
C:\HopeBackup\_deploy\deploy.cmd 10.0.0.9 ubuntu node
:: сервер управления
C:\HopeBackup\_deploy\deploy.cmd 10.0.0.5 ubuntu server
:: агент (команда с токеном и отпечатком — в панели: Агенты → Подключить агент)
C:\HopeBackup\_deploy\deploy.cmd 10.0.0.21 ubuntu agent https://10.0.0.5:4443 <токен> <отпечаток>
```

Скрипт определяет архитектуру сервера (x86_64 или ARM64), копирует основной бинарник и нужные сборки из
`bin\dist` (серверу управления — весь комплект: он нужен для описи и установки агентов на машины других
архитектур), проверяет SHA-256, распаковывает и запускает `linux/install.sh` с нужной ролью. На Alpine нужен
`sudo` (`apk add sudo`); `bash` скрипт поставит сам. Журнал — `_deploy\deploy_<IP>_<роль>.log`.

## 3. Установка на сервере вручную

### Из архива одним скриптом (рекомендуется)

Из `bin/release` положите на сервер, например в `/tmp`, два файла: `hopebackup-<версия>-linux.tar.gz` и
`hopebackup-install.sh`. Затем от root:

```sh
sh /tmp/hopebackup-install.sh                 # спросит, что ставить: server, node или agent
sh /tmp/hopebackup-install.sh server          # сервер управления — панель https://<IP>:4443/
sh /tmp/hopebackup-install.sh node            # узел площадки — порт 8443, копии в /var/lib/hopebackup-node
sh /tmp/hopebackup-install.sh agent --server https://10.0.0.5:4443 --token <токен> --fingerprint <отпечаток>
sh /tmp/hopebackup-install.sh status          # что установлено и работает ли
sh /tmp/hopebackup-install.sh uninstall       # удалить программу и службы (данные остаются; --purge — и данные)
```

Скрипт работает в любом `sh` (dash, busybox — в том числе Alpine) и сам:

* находит архив рядом со скриптом или в `/tmp` (или `--archive ФАЙЛ`), сверяет контрольные суммы;
* выбирает сборку под машину: x86_64 или aarch64, glibc ≥ 2.17 или статическая musl;
* агенту с уже существующей настройкой: без `--server`/`--token` оставляет её, с ними — **переподключает** к
  указанному серверу (прежняя настройка сохраняется рядом как `agent.json.before-<время>`), например при переносе
  агентов на другой сервер управления;
* проверяет память, место на диске (узлу — под копии), занятость порта, синхронизацию времени, наличие `ssh`;
* ставит программу в `/opt/hopebackup` (прежняя версия — `hopebackup.bak.*`, три последние), серверу —
  комплект сборок для машин других архитектур;
* настраивает роль: узлу — токены в `/var/lib/hopebackup-node/initial_tokens.txt` (0600), агенту — подключение
  к серверу (токен передаётся файлом, не в командной строке; без параметров спросит их);
* открывает порт в файрволе (ufw, firewalld, nftables, iptables; `--no-firewall` — не трогать), создаёт службу
  systemd или OpenRC, ждёт её запуска и печатает адрес панели, первый пароль и отпечаток сертификата.

Повторный запуск с той же ролью — обновление: данные, токены и адрес службы сохраняются (порядок обновления
узлов, обновление из панели и откат — [07_Обновление.md](07_Обновление.md)). Другие параметры:
`--listen АДРЕС:ПОРТ`, `--data КАТАЛОГ`, `--name ИМЯ` (агента), `--vpn openvpn,wireguard,l2tp,ipsec`
(пакеты VPN-коннекторов через apt, dnf/yum, apk или zypper), `-y` (без вопросов).

### Бинарником и install.sh

```bash
gunzip hopebackup.gz && chmod +x hopebackup
sudo BIN_SRC=./hopebackup MODE=node bash install.sh
sudo BIN_SRC=./hopebackup MODE=server bash install.sh
sudo BIN_SRC=./hopebackup MODE=agent SERVER=https://10.0.0.5:4443 TOKEN=… FINGERPRINT=… bash install.sh
```

Если основной бинарник на этой системе не запускается (ARM64, Alpine, glibc старше 2.17), `install.sh` берёт
подходящую сборку из комплекта — каталог `DIST_SRC` (по умолчанию `dist` рядом с `BIN_SRC`):

```bash
# ARM64 или Alpine: рядом с hopebackup — каталог dist из bin/dist
sudo BIN_SRC=./hopebackup DIST_SRC=./dist MODE=agent SERVER=… TOKEN=… FINGERPRINT=… bash install.sh
```

Серверу управления `install.sh` копирует комплект в `/opt/hopebackup/dist`.

Службы: `hopebackup-node`, `hopebackup-server`, `hopebackup-agent` — systemd или OpenRC (Alpine).
Журналы — `journalctl -u <служба>` или `/var/log/<служба>.log` (OpenRC).

Пакеты для VPN-коннекторов (на агентах и сервере, где они используются) ставятся параметром `VPN`:

```bash
sudo BIN_SRC=./hopebackup MODE=agent VPN=openvpn,wireguard,l2tp,ipsec SERVER=… TOKEN=… FINGERPRINT=… bash install.sh
```

| Коннектор | Пакеты (Debian/Ubuntu/Astra) | Примечание |
|---|---|---|
| OpenVPN | `openvpn` | профиль .ovpn — с сертификатами внутри |
| WireGuard | `wireguard-tools` (+ `wireguard-go`, если в ядре нет модуля) | ядро 5.6+ или модуль `wireguard` |
| L2TP/IPsec | `strongswan-swanctl charon-systemd xl2tpd ppp` | системная служба xl2tpd отключается: HopeBackup запускает свой экземпляр |
| IPsec IKEv2 | `strongswan-swanctl charon-systemd` | служба `strongswan` должна работать |

Если пакетов нет, после сохранения коннектора панель предложит установить их на сервере управления и на агентах, которые ходят через этот коннектор (`apt-get`/`dnf`/`yum`, нужен доступ к репозиториям дистрибутива). В закрытом контуре поставьте их заранее.

При остановке службы `ExecStopPost=hopebackup vpn-cleanup` убирает оставшиеся интерфейсы `hb*` и IPsec-соединения.

## 4. Узел площадки

При первой установке узел печатает (и сохраняет в `/var/lib/hopebackup-node/initial_tokens.txt`, 0600):

* **адрес** и **отпечаток сертификата** — вносятся в панель при добавлении площадки;
* **токен администратора** — для очистки по политике хранения (поле «Токен очистки» площадки);
* **токен агентов (append)** — для записи копий (поле «Токен» площадки).

На узле хранятся только хэши токенов. Новый токен: `hopebackup node token --name dc2-agents --role append`
(`--role read` — только восстановление, `--repo <имя>` — ограничить одним репозиторием).

Веб-панели у узла нет: в браузере по его адресу открывается страница-подсказка («Узел хранения HopeBackup»,
версия и, если на этой же машине работает сервер управления, кнопка «Открыть панель управления»). Панель — на
сервере управления, порт 4443.

Узел в закрытом сегменте без входящего доступа: оставьте 8443 закрытым снаружи и подключайтесь коннектором
«SSH-туннель» к SSH-серверу площадки (пользователь с ключом; в `authorized_keys` можно ограничить
`restrict,port-forwarding,permitopen="127.0.0.1:8443"`).

## 4а. Площадка в объектном хранилище (Yandex Cloud, AWS, MinIO)

Узел ставить не нужно: **Площадки → Добавить площадку → Yandex Object Storage / AWS S3 / S3-совместимое**.

* **Бакет** — заранее, при необходимости с **Object Lock** (Yandex: «Блокировка версий объектов»; AWS:
  `aws s3api create-bucket … --object-lock-enabled-for-bucket`). Срок хранения задаётся у площадки.
* **Ключ агентов** — только чтение, запись, список (без удаления). Yandex: сервисный аккаунт с ролью
  `storage.uploader` на бакет. AWS: политика `s3:ListBucket`, `s3:GetObject`, `s3:PutObject`,
  `s3:PutObjectRetention` (готовый JSON — в форме площадки).
* **Ключ очистки** (сервер) — дополнительно `s3:DeleteObject` (Yandex: `storage.editor`). Без него очистка
  по политике хранения не выполняется.
* С версиями бакета и Object Lock удаление ставит маркер удаления, данные живут до конца срока — для
  освобождения места настройте правило жизненного цикла «удалять неактуальные версии через N дней».

## 4б. Площадка на диске сервера управления

Примонтируйте большой диск (например, в `/mnt/data`) и в панели выберите **Площадки → Добавить площадку →
Диск сервера управления**: каталог (`/mnt/data/hopebackup`) и адрес сервера для агентов (`https://10.0.0.5:4443`).
Отдельный узел ставить не нужно — сервер обслуживает каталог сам, агенты пишут через порт 4443. Для каталога
на NFS/SMB смонтируйте его с правами записи для root.

## 4в. Площадка в облачном диске (Google Диск, Яндекс Диск, Nextcloud)

**Площадки → Добавить площадку → Google Диск / Яндекс Диск / Nextcloud / WebDAV.** Для Google и Яндекса
понадобится своё приложение OAuth (Client ID и секрет) — порядок в разделе «Площадки на диске и в облаке»
документа [02_Администрирование.md](02_Администрирование.md); вход — по коду на странице Google/Яндекса, токены
остаются на сервере. Для Nextcloud — адрес WebDAV, логин и пароль приложения. Агентам нужен исходящий HTTPS
к облаку (или прокси/VPN-коннектор).

## 4г. Принимающий узел управления

См. [03_Аварийное_восстановление.md](03_Аварийное_восстановление.md): второй сервер управления на резервной
площадке подключается к активному кодом приглашения («Узлы управления»).

## 5. Сервер управления

Панель и REST API — `https://<сервер>:4443/`. При обновлении сервера, где панель была на 7543, установка оставляет
7543 вторым адресом: агенты узнают новый порт из ответа сервера и сами переходят на 4443 (проверив тот же
сертификат). Когда все агенты перешли (раздел «Агенты», «в сети»), уберите старый порт:
`sudo LISTEN=0.0.0.0:4443 MODE=server BIN_SRC=… bash install.sh`.

### Серверы и ВМ без агента

**Серверы и ВМ → Добавить сервер**: адрес, порт SSH, пользователь (root или с sudo) и пароль — или закрытый ключ,
если пароли на машине запрещены (`PasswordAuthentication no`). Для sudo с паролем при входе по ключу — поле
«Пароль sudo». Серверу управления нужен исходящий доступ к машине по SSH; на машине ничего не устанавливается:
программа описи — сборка под архитектуру и библиотеку C машины (x86_64 или ARM64, glibc или статическая musl) —
копируется во временный каталог (при правах root — каталог root в `/var/tmp`) и удаляется после работы.
**Установить агента** ставит `/opt/hopebackup/hopebackup` и службу `hopebackup-agent` (systemd или OpenRC).


Панель: `https://<сервер>:4443/`. Пароль `Administrator` — в выводе установки и в
`/var/lib/hopebackup/server/initial_admin_password.txt`; смените его (Пользователи) и удалите файл.
Отпечаток сертификата сервера показывается при установке и в окне «Подключить агент».

Сразу после установки настройте **Почта и уведомления**: сервер почты организации и получателей уведомлений,
а в **Пользователи** — адреса почты. Тогда забытый пароль восстанавливается ссылкой «Забыли пароль?» на
странице входа, а администраторы узнают об ошибках копирования, нарушении RPO и пропавших агентах из писем.

## 6. PostgreSQL и qdatabase на агенте

1. Добавьте продукт **PostgreSQL 14+** или **qdatabase** (для qdatabase каталог `/opt/qdatabase-15.0/bin` подставлен).
2. «Обнаружить» — агент найдёт каталог бинарников, версию, каталог данных и проверит архивацию WAL.
3. «Настроить архив WAL» — `archive_mode`, `archive_command`, `archive_timeout`. Если `archive_mode` был
   выключен — перезапустите СУБД (`systemctl restart postgresql` / `pg_ctlcluster 16 main restart`).
4. Пользователь СУБД для копий: по умолчанию `postgres` по сокету (peer). Для отдельной роли:
   `CREATE ROLE backup LOGIN REPLICATION PASSWORD '…'; GRANT pg_read_all_data TO backup;`
   и строка `local replication backup scram-sha-256` в `pg_hba.conf`.

## 6а. Другие продукты на агенте

Агент ставится на машину с продуктом (или на гипервизор / узел с доступом к API платформы) и пользуется
штатными утилитами продукта — их нужно установить рядом с агентом (или указать контейнер Docker, в котором они
есть):

| Продукт | Утилиты на машине агента |
|---|---|
| MySQL / MariaDB | `mysql`/`mariadb`, `mysqldump`/`mariadb-dump`, `mysqlbinlog`; для физической копии — `mariabackup` + `mbstream` или `xtrabackup` + `xbstream` той же версии |
| MS SQL Server | `sqlcmd` (mssql-tools18 или go-sqlcmd) |
| MongoDB | MongoDB Database Tools (`mongodump`, `mongorestore`), по желанию `mongosh` |
| Redis / Valkey | `redis-cli` |
| ClickHouse | `clickhouse-client` |
| OpenLDAP / FreeIPA | `slapcat`, `slapadd` / `ipa-backup`, `ipa-restore` |
| Kubernetes | `kubectl` и kubeconfig; для снимка etcd — `etcdctl` на узле управления |
| Zabbix / Grafana | клиент MySQL или `pg_dump`/`pg_restore`; для Grafana — `sqlite3` (без него — короткая остановка) |
| Образы ВМ libvirt, OpenNebula, SpaceVM, VMmanager | на узле: `virsh`, `qemu-img` (агент на узле или вход по SSH) |
| Proxmox VE | на узле: `vzdump`, `qmrestore`, `pvesh` (агент на узле или вход по SSH под root) |
| oVirt, OpenStack, vSphere, XCP-ng, Nutanix | ничего: работа через API платформы по HTTPS |

Экземпляры добавляются в **Продукты → Добавить продукт**; анализ сервера («Серверы и ВМ») сам находит
работающие продукты и предлагает экземпляры с подставленными параметрами.

## 7. Сборка из исходников

```bash
cd admin && npm ci && npm run build            # панель → admin/dist (встраивается в бинарник)
cd ../hopebackup-core
pip install ziglang && cargo install cargo-zigbuild
cargo zigbuild --release --target x86_64-unknown-linux-gnu.2.17
gzip -9 -c target/x86_64-unknown-linux-gnu/release/hopebackup > ../bin/hopebackup.gz
cd .. && sha256sum bin/hopebackup.gz > bin/hopebackup.gz.sha256
```

Проверка: `hopebackup --version`. Сквозной тест на одной машине (root, PostgreSQL, OpenSSH, jq): `tests/e2e.sh`.

Комплект `bin/dist` (ARM64 и статические musl) собирается теми же исходниками — команды в `Как запускать.txt`, п. 3а.
