# HopeBackup — резервное копирование и восстановление инфраструктуры

HopeBackup снимает консистентные копии продуктов (продукты Hope — Mail Server, MSG Gateway, HopeInventory, HopeDFS,
HopeDC; PostgreSQL 14+, qdatabase, MySQL/MariaDB, MS SQL Server, MongoDB, Redis, ClickHouse; GitLab, Vault,
Keycloak, FreeIPA/LDAP, Docker, Kubernetes, Jenkins, Nexus/Harbor, Zabbix/Grafana, Elasticsearch/OpenSearch,
бакеты S3, nginx, HAProxy, OpenVPN, файлы, Linux-сервер целиком, образы ВМ libvirt, Proxmox, oVirt/zVirt, OpenNebula,
OpenStack, vSphere, XCP-ng, Nutanix, SpaceVM, VMmanager), передаёт на площадки, которые выбирает администратор.

Cвои узлы хранения, большой диск сервера управления, Yandex Object Storage, AWS S3, MinIO, Google Диск, Яндекс Диск,
Nextcloud — только новые, сжатые и зашифрованные блоки и восстанавливает систему на «чистый» сервер, новую ВМ
в Proxmox VE, VMware vSphere, Yandex Cloud или AWS — в том числе на заданный момент времени. 

Модуль «Переезд» переносит работающие Linux-машины (VMware, vCloud Director, Yandex Cloud, «железо») на Proxmox VE и zVirt/oVirt/РОСА с коротким простоем: синхронизации изменений, тест без сети, переключение и откат.

Принимающие узлы на других площадках держат реплику данных и каталога: при потере основной площадки оператор принимает управление и восстанавливает инфраструктуру оттуда. Продукт из линейки Hope (HopeDFS, HopeDC):

тот же стек (Rust + React/Tailwind), вид панели, роли и права, установка с Windows через PuTTY.

| | |
|---|---|
| Роли | **Сервер управления** (панель и API `https://сервер:4443/`, расписания), **узел площадки** (репозитории копий, `:8443`), **агент** на хосте с продуктом. Один бинарник `hopebackup`, роль задаётся командой |
| Продукты | **PostgreSQL 14+ и форки (qdatabase)**: `pg_basebackup` потоком, непрерывный архив WAL, PITR, `pg_dump`; установка нужной версии на чистую ВМ при восстановлении. **GitLab** (Omnibus и Docker): `gitlab-backup` без сжатия для дедупликации + `gitlab.rb` и `gitlab-secrets.json`, восстановление строго в ту же версию (с установкой из packages.gitlab.com). **Vault / OpenBao**: снапшот raft через API потоком, `snapshot-force`. **Бакеты S3**: объекты, тип и метаданные, большие объекты — потоком и частями. **Файлы**: пресеты nginx, HAProxy, OpenVPN с проверкой после восстановления. **Сервер Linux целиком**: опись процессов и скриптов, cron и таймеров, своих служб, дисков и сетевых каталогов, Docker, пользователей; копия /etc, пользователей с паролями и ключами SSH, домашних каталогов, найденных приложений; восстановление пользователей, частей или сервера целиком. **Исключения**: общий список сервера и у каждого экземпляра (`/var/log`, `*.log`, `node_modules`…) |
| Передача | FastCDC (блоки ~1 МиБ, границы зависят от ключа репозитория) → keyed BLAKE3 → пакетный вопрос площадке «каких блоков нет» → zstd → XChaCha20‑Poly1305 → pack-файлы по 16 МиБ. По каналу идут только новые блоки; повторы при обрыве связи |
| Площадки | **Узел HopeBackup** (в том числе ВМ в облаке), **диск сервера управления** (`/mnt/data`), **облачные диски** Google Диск, Яндекс Диск (вход по коду OAuth), Nextcloud/WebDAV и **объектные хранилища**: Yandex Object Storage, AWS S3, S3-совместимые (MinIO, Ceph RGW) — с Object Lock (WORM), классами хранения, раздельными ключами агентов (без удаления) и сервера (очистка). **Принимающие площадки**: всё, что попадает на площадку, реплицируется на другие (узел ↔ S3) как есть, удаления не повторяются |
| Коннекторы | **SSH-туннель (`-L`)** с jump-хостом, **OpenVPN** (профиль .ovpn, логин/пароль), **WireGuard** (ядро или wireguard-go/boringtun), **L2TP/IPsec** (strongSwan + xl2tpd), **IPsec IKEv2** (PSK или EAP; Yandex Cloud и AWS Site-to-Site VPN), **напрямую (TLS)**. Через VPN идёт только трафик до площадки: маршрут по умолчанию, DNS и скрипты сервера VPN не принимаются. Несколько коннекторов на площадку — по приоритету |
| Восстановление | **Сервер по SSH** (данные напрямую или через сервер по обратному туннелю), **сервер с агентом**, **новая ВМ**: Proxmox VE (клон шаблона, cloud-init), VMware vSphere 7+ (клон эталона или шаблона библиотеки, cloud-init или спецификация vCenter), Yandex Compute Cloud (сервисный аккаунт), AWS EC2. ВМ получает одноразовый ключ, после успеха появляется среди целей; при сбое удаляется |
| Серверы и ВМ | Подключение по SSH **по паролю** (в том числе keyboard-interactive) или **по ключу**, где пароли запрещены; sudo без пароля или с паролем; закрепление ключа хоста. **Опись до копирования** без установки чего-либо: ОС и версия, ядро, загрузка (UEFI/BIOS, Secure Boot, загрузчик, параметры ядра, initramfs, init), железо и виртуализация, диски (LVM, RAID, LUKS, fstab), сеть, SELinux/AppArmor/файрвол, процессы, задания, службы, пользователи. **Анализ и рекомендации**: что копировать, какими продуктами и с каким расписанием, оценка объёма, что учесть при восстановлении на новую ВМ. Установка агента и экземпляры по рекомендациям — кнопками |
| Надёжность копий | **Повторы** неудачных копий по расписанию (число попыток и пауза — у сервера или экземпляра), **догон** запуска, пропущенного, пока сервер был выключен. Падение сервера, агента или связи посреди копии не теряет итог и не оставляет битых точек: outbox агента, ожидание площадки до 10 минут, сверка со снапшотом, докачка только недостающего. **Снимки LVM / ZFS / btrfs** перед файловой копией. Анализ машины подсказывает, что донастроить: сколько места добавить в группу томов под снимки (с командами), память, процессор, время, сеть |
| Переезд | Блочная реплика дисков Linux-машины агентом (без драйверов ядра) или **ВМ vSphere без агента** (снимок, экспорт VMDK); синхронизации только изменённых блоков по расписанию и их применение на цели — **Proxmox VE** (тома в LVM/LVM-thin/ZFS/каталоге/Ceph) или **zVirt/oVirt/РОСА** (API Engine и imageio); ВМ создаётся с параметрами и MAC-адресами источника. Тестовый запуск без сети со снимком, переключение (остановка служб, заморозка ФС, выключение источника, запуск ВМ), откат. Подготовка к KVM: virtio в initramfs, имена интерфейсов по MAC, fstab по UUID |
| Обновления | Раздел «Обновления» в панели: сервер управления — архивом выпуска (закрытый контур) или онлайн по манифесту с обязательным SHA-256; установщик вне службы, ожидание ответа новой версии, **автоматический откат**. Агенты обновляются оттуда же — сборкой своей архитектуры из комплекта сервера. Порядок для узлов управления, агентов и площадок — `docs/07_Обновление.md` |
| Узлы управления | Активный и **принимающие** серверы управления: каталог (площадки, экземпляры, цели, пользователи, агенты) синхронизируется с подписью HMAC; «Принять управление» на принимающем узле при потере основной площадки; эпохи исключают два активных узла; агенты переключаются сами |
| Безопасность | Шифрование на источнике, мастер-ключ репозитория защищён паролем (Argon2id); площадка видит только шифротекст. Агенты не могут удалять копии (токен узла append / ключ S3 без удаления), очистку выполняет сервер с отдельными правами; Object Lock. TLS с закреплёнными отпечатками. Роли панели: администратор, оператор, восстановление, аудитор; журнал аудита |
| Доступ к панели | **«Забыли пароль?»** — одноразовая ссылка на почту пользователя (30 минут; без почты — в файле на сервере, только root); **аварийное восстановление** для закрытого контура — код запроса с отпечатком сервера → токен вендора (как в HopeDFS). Смена или сброс пароля закрывает открытые сеансы |
| Почта и уведомления | Сервер почты организации (STARTTLS, TLS, без шифрования; свой ЦС). Письма администраторам: ошибка и успех копирования, нарушена цель RPO, сбой отправки WAL, восстановление, агент не на связи, опись и установка агента, изменился ключ хоста машины, мало места, узлы управления, сброс пароля, подбор пароля; и когда состояние вернулось в норму. Журнал отправки |
| Платформы | x86_64 и **ARM64 (aarch64)**; glibc ≥ 2.17 и **musl** — статическая сборка для **Alpine без gcompat** и любых Linux. Сервер управления сам выбирает сборку для машины по архитектуре и библиотеке C; службы systemd и OpenRC |

| Путь | Что там |
|---|---|
| `bin/hopebackup.gz` | Основной бинарник: Linux x86_64, glibc ≥ 2.17 (CentOS/RHEL/Oracle 7+, Alma/Rocky 8+, РЕД ОС 7+, Debian 8+, Ubuntu 14.04+, SLES/openSUSE 12+, Astra Linux 1.6+, ALT 8+, МСВСфера), `.sha256` — контрольная сумма |
| `bin/dist/` | Комплект сборок: `hopebackup-x86_64-gnu.gz`, `hopebackup-x86_64-musl.gz` (статическая — Alpine и любые Linux), `hopebackup-aarch64-gnu.gz` (ARM64, glibc ≥ 2.17), `hopebackup-aarch64-musl.gz` (ARM64, статическая); `.sha256`. Установка сама берёт подходящую; серверу управления комплект нужен для машин других архитектур |
| `bin/release/` | **Установка на Linux:** `hopebackup-<версия>-linux.tar.gz` (все сборки) и `hopebackup-install.sh` — положите оба в `/tmp` и выполните `sh /tmp/hopebackup-install.sh` (роль спросит сам) |
| `linux/hopebackup-install.sh` | Исходник установочного скрипта (sh, systemd/OpenRC, обновление, удаление) |
| `linux/install.sh` | Установка роли на сервер: служба systemd, каталоги, файрвол | (для `deploy.cmd`)
| `_deploy/deploy.cmd`, `deploy.ps1` | Установка/обновление с Windows по SSH (PuTTY) |
| `hopebackup-core/` | Исходный код (Rust): движок хранения, узел, сервер, агент, плагины, коннекторы |
| `admin/` | Исходный код веб-панели (React + Vite + Tailwind), встраивается в бинарник |
| `docs/` | Документация в HTML — начните с `docs/index.html` (установка, администрирование, аварийное восстановление, переезд, обновление, архитектура, REST API, дорожная карта); исходники — Markdown рядом, HTML пересобирается командой `python3 hopebackup-core/tools/gen_docs.py` |
| `tests/` | Сквозные проверки на одной машине: `e2e.sh` (PostgreSQL → площадка → PITR по SSH, на новые ВМ Proxmox/VMware/Yandex Cloud/AWS через имитаторы API), `vpn.sh` (OpenVPN и WireGuard в сетевом пространстве «площадки»), `s3.sh` (площадка S3, Object Lock), `cluster.sh` (принимающие узлы и потеря площадки), `plugins.sh` (S3, Vault, GitLab), `host.sh` (сервер Linux целиком: опись, пользователи, приложения, диски), `storage.sh` (диск сервера, Nextcloud/WebDAV, Яндекс Диск, Google Диск), `machines.sh` (серверы и ВМ по SSH: пароль, ключ, опись, анализ, установка агента), `notify.sh` (почта, «Забыли пароль?», аварийный токен, уведомления), `arch.sh` (Alpine без glibc, ARM64 glibc и musl через qemu: выбор сборки, опись, агент на ARM), `resilience.sh` (падение сервера управления, агента и площадки посреди копии, повторы, сверка снапшота, догон расписания), `snapshot.sh` (снимки btrfs и LVM перед файловой копией), `install.sh` (установочный скрипт: systemd и OpenRC/Alpine, обновление, удаление), `replica.sh`, `migrate.sh`, `migrate_server.sh`, `migrate_vs.sh` (переезд: реплика на loop-устройствах под записью, цели Proxmox и zVirt/oVirt, оркестровка через сервер, vSphere без агента на настоящих VMDK streamOptimized, подготовка к KVM); `mocks/` — имитаторы API и заглушка SMTP |

## Быстрый старт

С Windows (нужен PuTTY в `tools\PuTTY` или `C:\HopeDFS\tools\PuTTY`):

```bat
C:\HopeBackup\_deploy\deploy.cmd 10.0.0.9  ubuntu node      :: узел на резервной площадке
C:\HopeBackup\_deploy\deploy.cmd 10.0.0.5  ubuntu server    :: сервер управления
```

1. Откройте `https://10.0.0.5:4443/` (панель и API — порт 4443), войдите как `Administrator` (пароль — в выводе установки и в
   `/var/lib/hopebackup/server/initial_admin_password.txt`).
2. **Площадки → Добавить площадку**: адрес узла, «Получить отпечаток», токен агентов и токен администратора
   из вывода установки узла, пароль репозитория (без него копии не восстановить — храните отдельно).
   При необходимости — **Коннекторы → SSH-туннель**. Затем «Создать репозиторий».
3. **Серверы и ВМ → Добавить сервер** (адрес, пользователь, пароль или ключ) → **Опись и анализ** → **Установить агента** →
   **Создать экземпляры по отмеченным** — или вручную: **Агенты → Подключить агент** — команда для хоста с СУБД. Установка агента:
   `deploy.cmd 10.0.0.21 ubuntu agent https://10.0.0.5:4443 <токен> <отпечаток>`.
4. **Добавить продукт → PostgreSQL 14+ (или qdatabase)** → «Обнаружить» → «Настроить архив WAL» (при первом
   включении — перезапуск СУБД) → «Полная копия». Расписание по умолчанию — полная копия ночью, WAL непрерывно.
5. **Цели восстановления → Сервер по SSH** и **Мастер восстановления**: точка или момент времени → цель →
   параметры → запуск.

Сборка из исходников: `cd admin && npm ci && npm run build`, затем
`cd hopebackup-core && cargo zigbuild --release --target x86_64-unknown-linux-gnu.2.17` (подробно — `Как запускать.txt`).

Перевод панели (RU / EN): строки в коде — `tr("русский текст")`, переводы — `admin/src/i18n_en.ts`. Новые строки
обернуть: `cd admin && node tools/i18n_wrap.cjs src`; что осталось без перевода: `node tools/i18n_check.cjs`.
